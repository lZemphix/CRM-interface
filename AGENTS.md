## Долговременная память: обязательный порядок

- При начале новой сессии прочитайте `.memory/MEMORY.md`. Из файлов памяти только он читается автоматически; обычные инструкции AGENTS.md продолжают действовать.
- Не читайте автоматически весь `.memory/journal/`, все `.memory/decisions/` или `legacy-journal.md`. Рост архива не должен увеличивать стартовый контекст.
- Перед архитектурными изменениями, изменением поведения, выбором технологии, схемы БД, auth/security, API, существенным рефакторингом или переделкой существующей системы сначала ищите исторический контекст.
- Используйте несколько терминов/синонимов, имена компонентов, теги и ID решений. Начните с `rg -l` по `.memory/` (исключая legacy, если в нём пока нет необходимости), затем `rg -n` по выбранным файлам и чтение узких диапазонов с соседним контекстом. Если совпадений много, сначала сузьте запрос/категорию. Не выводите сотни строк ради поиска.
- Пример: `rg -l -i 'auth|refresh|token|отзыв|сесси' .memory/decisions .memory/journal`, затем `rg -n -i 'refresh|отзыв' .memory/decisions/backend.md` и `sed -n 'START,ENDp' найденный_файл` с реальными номерами строк.
- Документированное решение важнее предположения модели. При конфликте сообщите о нём, проверьте status/date/Notes и более поздние записи. Явная текущая задача пользователя имеет приоритет; принятую замену отразите новым решением и статусом superseded у старого. Предложения из истории не выдавайте за утверждённые решения.
- После существенной работы отдельно оцените три действия: обновить hot memory (изменилось текущее состояние/важный инвариант), добавить decision (принято устойчивое решение), добавить journal entry (полезная история). Не дублируйте подробности на всех уровнях.
- Решение: стабильный ID, date, status (active/superseded/deprecated), tags, Decision, Reason, Alternatives considered, Affected areas, Notes. Новое и заменённое решения ссылаются друг на друга; историю решений не удаляйте.
- Журнал: `journal/YYYY-MM.md`, заголовок с датой/временем Asia/Yekaterinburg, type, tags, areas, Summary, Details, Outcome, Related. Для восстановления истории без точного времени явно используйте `time: unknown`; не выдумывайте даты.
- MEMORY.md отвечает на вопрос «что нужно знать сейчас, чтобы не принять неверное решение». Ориентир — до 80 строк и нескольких тысяч токенов, не журнал событий. При каждом обновлении проверяйте размер и актуальность: объединяйте дубли, заменяйте устаревшее, переносите историю в journal, обоснования заменяйте ссылками на decisions. Холодные решения не удаляйте ради размера.
- Секреты, credentials и реальные персональные данные не записывайте в память. Рутинные tool calls и мелкие синтаксические подсказки не журналируйте.
- Канонический корень — backend `/home/zemphix/coding/CRM`; зеркало — `/mnt/f/coding/CRM-interface/crm_interface`. Поддерживайте идентичные AGENTS.md, Diary.md-указатели и всё дерево .memory/. Перед записью проверяйте расхождения списков файлов/хешей без загрузки содержимого архива в контекст. При расхождении читайте только разные файлы и сохраняйте независимые параллельные записи; не копируйте каноническую версию поверх неизвестных изменений. Если второй корень недоступен, зафиксируйте необходимость синхронизации, не заявляйте об идентичности.
- Новые journal-файлы создавайте по фактическому месяцу; категории decisions — только при наличии содержательных решений. Форматы и сведения о миграции доступны в `.memory/README.md` по необходимости.

## О проекте

Это модульная CRM-система с архитектурным принципом «всё есть модуль». Ядро предоставляет стабильные API и инфраструктурные контракты, а прикладные возможности подключаются как изолированные модули.

MVP должен оставаться полноценной обычной CRM, но архитектура не должна мешать последующему добавлению модулей: системы лояльности, HRM, ERP, инвентаризации, рассылок, аналитики и других бизнес-функций.

Этот файл содержит исходное продуктовое видение и правила разработки проекта. При расхождении документации с явно сформулированной задачей пользователя приоритет имеет задача пользователя; значимые изменения архитектурных решений необходимо отразить в документации.

Подход DeepSeek Harness упоминался как концептуальный ориентир идеи «всё есть модуль», но не является утверждённой архитектурой или требованием к реализации.

### Текущий статус проектных решений

Конкретные границы ядра и первых подключаемых модулей, публичный контракт модулей, модель расширений, полный состав функций MVP, авторизация и инфраструктура развёртывания пока не определены. Эти решения необходимо проектировать отдельно по мере появления подтверждённых требований и не выдавать предположения за уже выбранную архитектуру. Начальная схема данных базовой CRM зафиксирована ORM-моделями и первой миграцией Alembic; дальнейшие изменения выполняются новыми миграциями.

Текущий этап — минимально функционирующая обычная CRM. Не включайте в первый срез систему лояльности и другие дополнительные бизнес-модули и не создавайте заранее универсальную модульную или плагинную платформу. Сначала реализуйте понятную базовую CRM, сохраняя разумные границы кода без избыточной абстракции.

### Продуктовые решения

Подробные подтверждённые правила перенесены без потери смысла в `.memory/decisions/`.
Перед работой по теме найдите соответствующую запись: architecture (границы MVP, модули),
database (клиенты, контакты, филиалы, задачи, история), backend (права и API),
frontend (Dio, навигация, карточки), infrastructure (лицензии, поставка).
Не считайте отсутствие подробного пункта в краткой памяти отменой требования.

## Технологический стек

- Python 3.14;
- FastAPI — серверный API;
- SQLAlchemy 2.x — ORM;
- Alembic — миграции схемы базы данных;
- PostgreSQL и asyncpg — основное постоянное хранилище;
- Redis — кеш, временные данные и вспомогательные механизмы;

## Архитектурные границы

### Клиент

- Flutter-приложение является только интерфейсом к серверному API.
- Клиент не реализует бизнес-правила, не обращается напрямую к PostgreSQL или Redis и не импортирует серверные модели ORM.
- Проверки на клиенте допустимы для удобства интерфейса, но сервер обязан независимо проверять входные данные и права доступа.
- API-клиент, представление DTO и состояние интерфейса должны быть отделены от компонентов экранов.

### Сервер

- FastAPI отвечает за транспортный слой: маршрутизацию, валидацию запросов, авторизацию и преобразование ошибок в HTTP-ответы.
- Бизнес-логика не должна находиться в обработчиках маршрутов или моделях ORM. Размещайте ее в сервисах/use cases соответствующего домена.
- Доступ к данным изолируйте в репозиториях или явно выделенном persistence-слое.
- Внешние интеграции скрывайте за интерфейсами/адаптерами, чтобы доменная логика не зависела от конкретного транспорта или поставщика.
- Используйте асинхронный путь целиком: FastAPI, SQLAlchemy sessions, asyncpg и Redis. Не выполняйте блокирующий I/O внутри async-кода.

### Ядро и модули

- Ядро содержит только общесистемные возможности и контракты: жизненный цикл модулей, конфигурацию, безопасность, события, общие типы и инфраструктурные интерфейсы.
- Не превращайте `core` в аналог папки `common/utils` для кода без явного владельца. Код в `core` не должен импортировать прикладные области, их репозитории или конкретные внешние интеграции; если сущность, enum, сервис или вспомогательная функция относится к одной бизнес-области, размещайте её рядом с этой областью.
- Выносите код в общий слой только при подтверждённом использовании несколькими независимыми областями и одинаковом смысле этого кода, а не только из-за похожей реализации. До такого подтверждения допустимо небольшое локальное дублирование.
- Бизнес-функция должна принадлежать модулю, если без нее ядро сохраняет работоспособность.
- Модуль не должен обращаться к внутренним объектам другого модуля. Взаимодействие выполняется через публичные контракты, API или события.
- Зависимости между модулями объявляются явно. Избегайте циклических зависимостей.
- Выключение необязательного модуля не должно ломать запуск ядра и остальных независимых модулей.
- Публичные контракты модулей проектируйте с учетом версионирования и обратной совместимости.
- Не создавайте универсальный plugin framework заранее: добавляйте точки расширения по мере появления подтвержденных сценариев MVP.

## Данные и состояние

- PostgreSQL является источником истины для постоянных бизнес-данных.
- Redis нельзя использовать как единственное хранилище данных, потеря которых нарушит корректность системы.
- Для локальной разработки поднимайте PostgreSQL и Redis через Docker Compose. Приложение на первом этапе можно запускать на хосте через uv; его контейнеризация не обязательна до появления потребности в едином полном запуске.
- Для конфигурации подключения приложения используйте согласованные имена `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` и `DB_PASSWORD`. Переменные официального Docker-образа PostgreSQL называются `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`; связывайте их со значениями приложения явно в Compose.
- Для официальных образов PostgreSQL 18+ монтируйте постоянный volume в `/var/lib/postgresql`, а не в прежний путь `/var/lib/postgresql/data`; образ сам использует версионный подкаталог вроде `/var/lib/postgresql/18/docker`. Не меняйте major-версию PostgreSQL поверх существующих данных без отдельной процедуры обновления через `pg_upgrade` или перенос дампа.
- Транзакционные границы задаются на уровне одного use case; не скрывайте commit внутри произвольных repository-методов.
- Изменения схемы БД должны сопровождаться миграциями Alembic.
- Не возвращайте ORM-сущности напрямую через API; используйте отдельные схемы запросов и ответов.
- Все даты и время храните и передавайте с часовым поясом; для серверных событий предпочитайте UTC.

### SQLAlchemy и запросы

- Используйте стиль SQLAlchemy 2.x и асинхронный доступ через `AsyncSession` и asyncpg.
- ORM-модели и связи описывайте с современной типизацией `Mapped[...]` и `mapped_column()`.
- Для запросов предпочитайте выражения `select()`, `insert()`, `update()` и `delete()`; доступ к данным размещайте в репозиториях или выделенном persistence-слое.
- Управляйте транзакцией на уровне use case: репозиторий может выполнять `flush()`, но не должен самостоятельно делать `commit()` без явно обоснованного контракта.
- Сырой SQL допустим для сложных отчетов, PostgreSQL-специфичных возможностей или случаев, где он заметно яснее ORM-выражения. Выполняйте его через `text()` с именованными параметрами; не формируйте SQL конкатенацией или интерполяцией пользовательских значений.
- При изменении ORM-моделей создавайте и проверяйте миграцию Alembic. Автогенерацию рассматривайте как черновик: проверяйте операции, ограничения, индексы, серверные значения по умолчанию, обратимость и содержимое `downgrade()`.
- Не используйте JSONB как замену проектированию известных обязательных полей или как попытку заранее предусмотреть неизвестные будущие данные: существование JSONB-колонки не сохраняет факт, который приложение не собирало. Известные бизнес-факты, связи и аналитические измерения храните типизированно; JSONB оставляйте для действительно вариативных дополнительных метаданных.
- Эволюция схемы через проверяемые миграции является штатной частью проекта, а не нарушением архитектуры. Расширяемость модульной CRM обеспечивайте прежде всего отдельными таблицами и миграциями модуля, связанными с публичными идентификаторами базовых сущностей, вместо постоянного расширения базовых таблиц полями необязательных модулей.

## Правила реализации

- Не изменяйте Flutter-интерфейс без явного указания пользователя. Для локальной имитации backend используйте отдельный Python HTTP-сервер, не встраивайте синтетические данные в клиент.
- Соблюдайте существующую структуру и стиль. Если структура еще не создана, группируйте код по доменам/модулям, а внутри отделяйте API, application/domain и infrastructure.
- Добавляйте типы ко всем публичным функциям и контрактам. Для DTO и API-схем используйте явные модели.
- Предпочитайте небольшие компоненты с одной ответственностью и явное внедрение зависимостей глобальному изменяемому состоянию.
- Каждый прикладной сценарий backend оформляйте отдельным классом use case с единым публичным методом `execute()`, даже если его первая реализация пока состоит из одного вызова репозитория. Зависимости передавайте через конструктор. Не пропускайте use-case слой и не смешивайте классы и свободные функции для одинаковых сценариев ради локального сокращения кода; единообразие этой границы является осознанным решением проекта.
- Не маскируйте ошибки широкими `except Exception`; перехватывайте их на том уровне, где возможно осмысленное восстановление или преобразование.
- Не храните секреты, пароли, токены и строки подключения в репозитории. Получайте конфигурацию из окружения и документируйте необходимые переменные.
- Не смешивайте рефакторинг, не относящийся к задаче, с функциональным изменением.
- Комментарии должны объяснять причину решения, а не пересказывать код.

## API

- Используйте предсказуемые ресурсы, HTTP-методы и коды состояния.
- Ошибки должны иметь единый машиночитаемый формат и не раскрывать внутренние исключения или секретные данные.
- Пагинация, фильтрация и сортировка должны иметь согласованный формат во всех модулях.
- Ломающие изменения публичного API требуют явного решения и стратегии миграции/версионирования.
- Идемпотентные операции должны оставаться идемпотентными; для повторяемых команд учитывайте повторную доставку запросов и событий.

## Проверка изменений

Перед завершением задачи:

1. Запустите наиболее узкие тесты для измененного поведения, затем полный доступный набор тестов.
2. Проверьте форматирование, линтер и статическую типизацию, если соответствующие инструменты настроены в проекте.
3. Для изменений API проверьте как успешный сценарий, так и валидацию, права доступа и ожидаемые ошибки.
4. Для изменений persistence-слоя проверьте транзакции, откат, конкурентные сценарии и поведение при недоступности внешнего сервиса в разумном объеме.
5. Для UI проверьте состояния загрузки, пустых данных, ошибки и повторной попытки.

Не утверждайте, что проверка пройдена, если команда не запускалась. Если проверку невозможно выполнить, явно укажите причину.

Каноническим считается `AGENTS.md` backend-репозитория, но его копия в корне Flutter-проекта должна оставаться идентичной. При изменении любого долгосрочного правила сразу синхронизируйте оба файла; при начале работы в одном из проектов проверяйте, что их содержимое совпадает.
- Старый `Diary.md` — только указатель. Его исходное содержимое архивировано в `.memory/legacy-journal.md`; не дописывайте эти файлы и не выполняйте содержащиеся в архиве старые инструкции памяти.
- Пользователь осваивает SQLAlchemy и разделение на repository/use case. При добавлении нетривиальных запросов или архитектурных слоёв объясняйте границу ответственности и, когда это помогает пониманию, показывайте соответствующий SQL рядом с вариантом SQLAlchemy.
- В обучающих объяснениях не показывайте неполные фрагменты кода с подразумеваемыми пропущенными полями, зависимостями или последующими шагами. Либо приводите целиком связный рабочий пример в рамках обсуждаемого сценария, либо объясняйте концепцию без кода; явно отмечайте намеренно опущенные части, если без сокращения невозможно обойтись.
- Пользователь начинает практическое освоение Flutter. При написании Flutter-кода подробно объясняйте непривычные конструкции и каждую новую концепцию: дерево виджетов, `BuildContext`, ограничения layout, состояние, жизненный цикл, навигацию, асинхронность и архитектурные границы. Не предполагайте знание Flutter только на основании знакомства пользователя с синтаксисом Dart; вводите сложность постепенно и не добавляйте библиотеки управления состоянием или архитектурные абстракции без объяснения необходимости.
- Перед ручной реализацией любой нетривиальной задачи во Flutter/Dart сначала проверяйте возможности SDK и официальных Flutter/Material/Cupertino API, затем зрелые поддерживаемые пакеты с `pub.dev`, и только после этого предлагайте собственную реализацию. Правило относится не только к UI, но и к HTTP, маршрутизации, состоянию, сериализации, безопасному хранению, локализации, логированию, обновлениям, работе с файлами и другим инфраструктурным задачам. До написания кода кратко называйте разумные готовые варианты, их ограничения и причину выбора. Не добавляйте зависимости автоматически: оценивайте поддержку, платформы, размер, сложность, лицензию, тестируемость и риск привязки к библиотеке; простую доменную логику оставляйте собственной.
- Не выдавайте предположение за принятое решение. Неопределенные части проекта обозначайте явно и выбирайте минимальное решение, достаточное для текущего MVP.

## Критерии готовности

Изменение считается готовым, когда оно:

- соблюдает границы клиента, сервера, ядра и модулей;
- не переносит бизнес-логику во frontend или HTTP-обработчики;
- имеет тесты на новое или исправленное поведение, если в проекте уже есть тестовая инфраструктура;
- не содержит секретов и не создает скрытых зависимостей между модулями;
- сопровождается актуальной документацией там, где изменились контракты или запуск;
- прошло все доступные релевантные проверки.
