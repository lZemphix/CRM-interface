## WORK-01 — Реализация backend и ревью

date: 2026-09-19
status: superseded
tags: review, commits, backend, tests, workflow

Decision:
Ассистент реализует backend небольшими законченными этапами по DEVELOPMENT_GUIDE.md и поздним подтверждённым решениям. После тестов и краткого отчёта пользователь проводит ревью; замечания исправляются в том же этапе. Коммит только после явного одобрения; push/деплой — отдельное поручение.
После каждой контрольной точки отчёт содержит полный список изменённых файлов этапа с кликабельными ссылками, порядок чтения и ключевые вопросы для ревью. Изменения иных этапов/параллельной работы отделяются.

Reason:
Пользователь понимает Python и берёт ревью; главные критерии — безопасность, стабильность, надёжность.

Alternatives considered:
Один большой непроверяемый этап и коммит до ревью не соответствуют выбранному процессу.

Affected areas:
backend, документация, Git

Notes:
Заменено WORK-03 2026-09-20: пользователь перешёл к приёмке поведения вместо обязательного построчного ревью. Чтение/объяснение кода само по себе не является одобрением коммита. Тесты идут вместе с поведением.

## WORK-03 — Приёмка поведения и риск-ориентированное ревью

date: 2026-09-20
status: active
tags: review, acceptance, commits, backend, security, workflow

Decision:
Ассистент реализует backend небольшими законченными этапами, сам проверяет дифф, тесты и риски и предоставляет пользователю краткий отчёт о поведении, контракте, ограничениях и изменённых файлах. Пользователь принимает результат по сценариям и бизнес-правилам; построчное ревью Python-кода не обязательно. Auth, права, миграции, безопасность и развёртывание требуют более тщательного отчёта и по возможности независимого ревью до использования реальных данных. После каждой контрольной точки ассистент останавливается для приёмки. Коммит этапа — только после явного одобрения; push и развёртывание — отдельные действия.

Reason:
Пользователю нужно ускорить разработку, а самостоятельное построчное ревью незнакомого SQLAlchemy даёт меньше пользы, чем проверка реальных сценариев и спорных правил. При этом отказ от проверки опасен для CRM с персональными данными.

Alternatives considered:
Обязательное построчное ревью каждого этапа (WORK-01) замедляет работу; отсутствие приёмки и проверок не подходит.

Affected areas:
backend, тесты, отчёты, Git, AGENTS.md

Notes:
Заменяет WORK-01 только в процедуре ревью. Небольшие этапы, тесты и запрет коммита без одобрения остаются. Пользователь уже одобрил этап POST /customers 2026-09-20.

## WORK-04 — Приоритет рабочего MVP без архитектурных тупиков

date: 2026-10-03
status: active
tags: mvp, scope, optimization, maintainability, frontend

Decision:
Сначала доводить необходимые сценарии до рабочего MVP. Не тратить этот этап на преждевременные оптимизации и обработку маловероятных случаев. При этом не выбирать временные решения, для улучшения которых затем потребуется глобальное переписывание: сохранять понятные границы ответственности и типизированные контракты.

Reason:
Оптимизировать ещё не готовый продукт преждевременно, но накопление заведомого архитектурного долга осложнит развитие после MVP.

Alternatives considered:
Оптимизировать всё заранее; ради скорости возвращать неструктурированные данные и смешивать транспорт с UI. Оба подхода отклонены.

Affected areas:
Планирование MVP, Flutter-клиент, API-интеграция, технические решения.

Notes:
Применять соразмерно задаче: типизированная DTO для ответа API — базовое качество контракта, а не преждевременная оптимизация.

status: active

Affected areas:

## MEM-03 — Независимая память frontend

date: 2026-09-24
status: active
tags: memory, retrieval, frontend, repository-boundary

Decision:
Механизм краткой hot memory, выборочного поиска и холодного архива сохраняется, но `AGENTS.md`, `Diary.md` и `.memory/` принадлежат только Flutter-репозиторию и больше не синхронизируются с backend. Backend ведёт другой исполнитель; его файлы не изменяются без отдельного явного поручения. Для совместимости клиент опирается на подтверждённый API-контракт, который при необходимости проверяется read-only.

Reason:
Параллельная независимая работа разных исполнителей делает общую двустороннюю память источником конфликтов и устаревших статусов.

Alternatives considered:
Продолжать зеркалировать инструкции и память между репозиториями — отклонено пользователем.

Affected areas:
AGENTS.md; .memory/; Diary.md; граница Flutter/backend

Notes:
Исторические backend-решения в холодном архиве не удаляются, но не считаются источником текущего статуса backend. MEM-02 сохраняет историю первоначальной общей системы памяти.
