# Дневник проекта CRM

Этот файл — долговременная память связанных backend- и Flutter-проектов. Он хранит не только действующие правила, но и контекст решений: что обсуждалось, к чему пришли, почему и что осталось открытым. Краткие нормативные требования находятся в `AGENTS.md`.

Правила ведения:

- после содержательного обсуждения добавлять датированную запись;
- фиксировать вопрос, решение, мотив и открытые продолжения;
- не выдавать предложение за утверждённое решение;
- при изменении решения не стирать историю, а добавлять новую запись со ссылкой на отменённый подход;
- синхронно обновлять копии в backend и Flutter;
- мелкие вопросы синтаксиса записывать только тогда, когда они повлияли на архитектуру или рабочий процесс.

## Ретроспективная сводка предыдущих обсуждений

Сводка восстановлена 2026-09-14 по текущему коду, `AGENTS.md` и истории диалога. У отдельных решений нет точной даты принятия.

### Назначение и поставка продукта

- Создаётся обычная модульная CRM для конкретных компаний, а не SaaS. Каждая компания получает выделенный backend и БД на своём сервере.
- Продукт ориентирован в том числе на небольшой бизнес: парикмахерские, магазины и клиники. Поэтому базовый сценарий не должен требовать сложных корпоративных ограничений.
- Одна серверная установка обычно обслуживает все филиалы компании. Количество активных филиалов лицензируется; закрытый филиал можно заменить новым в пределах лимита.
- Лицензируются и рабочие места: до пяти на филиал входят в базовую стоимость, дополнительные оплачиваются. Надёжный способ идентификации рабочего места пока не выбран.
- Клиент компании — нативное Flutter-приложение. Заказчику предоставляется интерфейс, но не административный доступ к backend.

### Путь от Flet к Flutter

- Сначала интерфейс прототипировался на Flet. Был собран дизайн CRM и рабочий прототип, но выяснилось, что сложная desktop-вёрстка требует обходных решений и плохо подходит под желаемый уровень интерфейса.
- Рассматривались проблемы запуска Flet из WSL и графического стека WSLg. Нативный запуск через Windows заработал, но это не изменило архитектурных ограничений Flet.
- Принято окончательное решение перейти на Flutter. Пользователь знает синтаксис Dart, но изучает устройство Flutter с нуля и просит объяснять каждую конструкцию явно, без пропущенных промежуточных шагов.
- Backend и Flutter находятся в отдельных связанных репозиториях. Это осознанное разделение, а не попытка превратить backend в микросервисы.

### Архитектурное понимание backend

- Репозиторий отвечает за способ хранения и извлечения данных: SQLAlchemy, таблицы, `SELECT`, `INSERT`, загрузку связей.
- Use case отвечает за бизнес-действие и не должен знать названия таблиц и колонок. Для единого стиля утверждены классы use case с методом `execute`, даже если действие пока небольшое.
- DTO используются как типизированные снимки входных команд, запросов и результатов между слоями. Пользователь уже применял такой подход в других проектах через замороженные dataclass, не называя его DTO.
- FastAPI-схемы описывают HTTP-контракт, DTO — application-контракт, ORM-модели — хранение. Эти роли не следует смешивать.
- SQLAlchemy используется асинхронно. `AsyncSession` — единица работы с БД; транзакцией управляет use case, а repository выполняет операции через переданную сессию.
- Разделение на слои принято не ради усложнения, а чтобы application-логика не зависела от конкретной таблицы и транспорта.

### Текущая реализация backend

- Используются FastAPI, SQLAlchemy 2.x async, PostgreSQL, Alembic, Pydantic Settings и `uv`.
- Создана первая миграция и ORM-модели клиентов, контактов, заметок, сотрудников, ролей, permissions, филиалов, задач, истории назначений/статусов и общего аудита.
- Реализованы `CustomerRepository`, `ListCustomersUseCase`, `CreateCustomerUseCase`, DTO и HTTP-ручка `GET /customers?limit=&offset=`.
- В БД можно загрузить демонстрационных клиентов отдельным seed-скриптом; демонстрационные данные не должны запускаться из production `main`.
- На 2026-09-14 backend-тесты проходят: 9 тестов.

### Клиенты и контакты

- `customers` — физические лица, то есть клиенты компании. `employees` — сотрудники.
- У клиента есть имя, пол, дата рождения, статус, домашний филиал, ответственный сотрудник, создавший запись сотрудник, первоначальный источник привлечения и метод регистрации.
- Возраст не хранится, потому что вычисляется из даты рождения.
- Контакты вынесены в отдельную таблицу: у клиента может быть несколько телефонов и других каналов, один контакт каждого типа может быть основным. Контакты архивируются, а не теряются.
- К карточке клиента добавлены отдельные заметки с автором и временем создания/редактирования.
- Переназначение ответственного хранится отдельной историей, чтобы разбирательства и аналитика не зависели только от текущего значения.

### Первоначальное привлечение и последующие обращения

- В карточке клиента хранится первоначальный источник — как он впервые узнал о компании. Источник использует стабильный машинный код и управляемое отображаемое название.
- Отдельно хранятся конкретный клиент-реферер и технический метод регистрации: сотрудник, самостоятельная регистрация, импорт или интеграция.
- Если достоверный первоначальный источник неизвестен, используется честное значение `unknown`; сотрудник не должен придумывать источник ради заполнения обязательного поля.
- Первоначальный источник нельзя смешивать с акциями последующих визитов. Клиент мог впервые прийти по рекомендации, второй раз — по акции, третий — по необходимости.
- Принято хранить историю каждого посещения/обращения отдельными записями со своими датой, причиной, кампанией/акцией и результатом. Связь концептуально выглядит как `Customer 1 → N Interaction`.
- Открыт вопрос о названии и универсальности сущности: базовая `interaction`, специализированная `visit/appointment` или несколько связанных сущностей. Таблица ещё не создавалась.

### Задачи

- Базовая CRM-задача относится к клиенту; задачи филиала без клиента могут появиться в отдельном будущем модуле.
- Для задачи обязательны автор, срок и приоритет. Исполнитель и комментарий могут отсутствовать, чтобы новая задача оставалась в общей очереди.
- Назначать задачу другому сотруднику может пользователь с отдельным руководящим permission, а не пользователь с захардкоженным названием роли.
- Утверждён цикл: `new → in_progress → completed → confirmed`. Если автор не принял работу: `completed → rework → in_progress`, затем задача снова завершается и проверяется. `confirmed` и `cancelled` — конечные состояния.
- В текущей ORM-модели на 2026-09-14 ещё отсутствуют `rework` и `confirmed`, а `customer_id` и `due_at` допускают `NULL`. Это известное расхождение, которое нужно исправить новой миграцией.

### Сотрудники, филиалы и права

- Каждый сотрудник имеет собственную учётную запись; общие аккаунты филиала не допускаются.
- Первого администратора создаёт сотрудник поставщика и выдаёт одноразовый пароль с обязательной сменой при первом входе.
- Один сотрудник может состоять в нескольких филиалах, один из них основной.
- Обычный доступ сотрудника к задачам ограничивается его филиалами. Сводная аналитика всех филиалов требует отдельного права.
- Уровни Cisco/Linux обсуждались только как понятная аналогия. В реализации используются конкретные permissions по категории и действию: `customers.read`, `customers.create`, `customers.update`, `customers.archive`, `tasks.assign`, `audit.read` и подобные.

### Аудит и аналитика

- Общий audit log нужен для технического и безопасностного следа: входы, ошибки, действия и метаданные запроса.
- Важные бизнес-изменения дополнительно хранятся в структурированных историях соответствующих сущностей. Это необходимо для достоверных разбирательств и будущей аналитики.
- Аналитика будет отдельным модулем, но базовые модули обязаны заранее сохранять структурированные факты. Аналитический модуль не должен восстанавливать статистику из произвольного JSON общего аудита.

### Границы модулей

- MVP содержит минимальную обычную CRM без системы лояльности и лишних возможностей.
- B2B является отдельным будущим модулем со своими сущностями и интерфейсом. Базовую B2C-таблицу нельзя заранее превращать в универсального контрагента.
- Сделки и воронки не входят в базовый CRM-прототип и планируются модулем `deals`.
- Аналитика и система лояльности также являются отдельными модулями.
- Пользовательская модель напоминает VS Code: включённый модуль добавляет свой пункт в левую навигацию и собственный раздел.
- На текущем этапе все официальные backend- и Flutter-модули заранее входят в общую сборку, но отключённые или нелицензированные модули скрыты и недоступны. Backend всегда проверяет лицензию самостоятельно.
- Такой подход выбран как самый простой для первой версии. Если Flutter-сборка станет чрезмерно большой, модель поставки будет пересмотрена по фактическим измерениям.
- Динамическая загрузка неизвестного Dart-кода в собранное Windows-приложение не планируется.

### Лицензирование и обновления

- Дополнительный модуль покупается на всю компанию и включается сотрудником поставщика через внутреннюю CRM поставщика.
- После отключения модуля его данные сохраняются, но штатный доступ блокируется.
- Обсуждалась ручная регистрация компании, филиалов и установок ответственным сотрудником поставщика. Точный криптографический протокол лицензирования пока не утверждён.
- Нельзя считать скрытие Flutter-экрана защитой: сервер должен проверять лицензию и permissions на каждом защищённом действии.
- Нельзя вшивать постоянный секретный мастер-ключ в `exe`. Обновление должно проверяться цифровой подписью; публичный ключ проверки может находиться в клиенте.
- Обсуждались самообновление через отдельный updater/MSIX и ручное обновление сотрудником поставщика. Окончательный процесс пока не утверждён; в действующих правилах первым production-клиентам обновления выполняет сотрудник поставщика.

### Flutter-архитектура

- `MaterialApp` создаёт корень приложения, `AppShell` — постоянную оболочку со sidebar и областью активного экрана.
- Sidebar не копируется в каждый экран. `AppShell` хранит выбранный `AppScreen`, передаёт sidebar текущее значение и callback переключения.
- Hover остаётся локальной визуальной реакцией sidebar; выбранный экран является состоянием `AppShell`.
- Бизнес-код интерфейса группируется по модулям, например `lib/modules/customers/`, внутри которого находятся `screens`, `widgets`, `models`, а позднее `data/repositories` и состояние.
- Создан Dart DTO `Customer.fromJson`, соответствующий текущему ответу `GET /customers`.
- Общий HTTP-клиент должен знать базовый URL, заголовки, сериализацию и ошибки транспорта. Репозиторий конкретного модуля должен знать его endpoints и преобразование DTO. На 2026-09-14 этот слой ещё не реализован.
- Клиент не обязан получать каждое изменение через WebSocket. Для MVP достаточно HTTP и повторной загрузки после собственных операций; WebSocket добавляется только для действительно необходимых внешних обновлений.

### Аутентификация

- Роль, идентификатор сотрудника и timestamp нельзя принимать от клиента как доказательство личности.
- Планируется access token для API и refresh token для обновления сессии. Access token передаётся в `Authorization: Bearer ...` через HTTPS; refresh token используется только на специальной ручке обновления.
- Точный механизм выпуска, хранения, ротации и отзыва токенов ещё не реализован и требует отдельного проектирования.

### Стиль совместной работы

- Пользователь изучает SQLAlchemy и Flutter с начального уровня, но не хочет временно учиться на заведомо плохой архитектуре ради упрощения.
- Объяснения должны раскрывать происхождение объектов и полный путь данных. Нельзя внезапно использовать `session`, dependency или скрытую ORM-загрузку без объяснения.
- Если приводится код, он должен быть цельным в рамках объясняемого сценария; разрозненные фрагменты с фразой «остальное подставится само» мешают обучению.
- Реализацию можно вести небольшими завершёнными шагами: после каждого шага объяснить, что сделано, зачем и как проходит управление.

## Запись 2026-09-14 — разработка Flutter до готовности backend

Вопрос: требуется ли полностью готовый backend, чтобы продолжать разработку интерфейса?

Решение: нет. Flutter можно разрабатывать от согласованного HTTP-контракта через отдельный mock-сервер, который возвращает реалистичные фиктивные ответы в точно таком же JSON-формате, кодах состояния и структуре ошибок, какие ожидаются от production API. Это позволяет независимо собирать списки, карточки, состояния загрузки, пустые результаты, ошибки и пагинацию.

Mock не является вторым источником API-контракта и не должен попадать в production-запуск. Формат запросов и ответов задаётся backend-схемами/OpenAPI; при изменении контракта одновременно обновляются DTO Flutter и mock-ответы. Позднее смена mock на реальный backend должна требовать только замены base URL или реализации источника данных, а не переписывания UI.

## Запись 2026-09-14 — вторичная строка карточки клиента

В компактной карточке клиента источник привлечения признан малополезным для ежедневной работы. Вместо него следует показывать давность последнего посещения/обращения: например, `1 дн.`, `3 нед.`, `2 мес.`, `1 г.`; для отсутствующей истории — `Нет визитов`. Backend должен возвращать точную дату/время последнего события (`last_interaction_at` или окончательное аналогичное поле), а Flutter вычисляет локализованную относительную подпись. Источник привлечения сохраняется в данных и остаётся доступен в подробной карточке, фильтрах и аналитике.

## Запись 2026-09-14 — готовые возможности Flutter перед ручной реализацией

Пользователь обнаружил, что при обучении не были своевременно показаны встроенные высокоуровневые компоненты Flutter, из-за чего некоторые элементы могли реализовываться вручную без сравнения с готовыми решениями. Принят рабочий порядок: сначала рассматривать встроенные Material/Cupertino-виджеты, затем зрелые пакеты `pub.dev`, затем собственный компонент. Выбор должен учитывать соответствие дизайну, сложность настройки, поддержку, платформы и цену дополнительной зависимости.

Для текущей левой desktop-навигации ближайший встроенный аналог — `NavigationRail`; `NavigationBar` предназначен прежде всего для нижней Material-навигации. Собственный sidebar всё ещё может быть оправдан VS Code-подобным дизайном, но альтернативу следовало назвать до реализации.

Уточнение пользователя: правило не ограничивается UI-компонентами. Оно распространяется на весь стек Flutter/Dart. Пример правильного применения — предложить `dio` вместо самостоятельного наращивания повторяющейся сетевой инфраструктуры поверх минимального HTTP-клиента. Аналогично перед реализацией навигации, управления состоянием, JSON-кода, защищённого хранения, локализации, логирования и обновлений необходимо рассмотреть существующие стандартные средства и зрелые библиотеки. Цель — не максимальное число зависимостей, а отказ от повторного решения сложных типовых задач при наличии качественного готового инструмента.

## Запись 2026-09-14 — HTTP-клиент Flutter

Для сетевого слоя Flutter выбран `dio`. Один общий экземпляр `Dio` будет хранить `baseUrl`, таймауты, общие заголовки и позднее interceptors авторизации; repository каждого модуля получает этот клиент и знает только endpoints своего домена и преобразование JSON в DTO. UI не должен вызывать `Dio` напрямую. Выбор сделан из-за будущих access/refresh token, единообразной обработки ошибок, отмены запросов и загрузки файлов; эти возможности будут добавляться по мере появления реального сценария, а не заранее.

При первом объяснении `dio` одновременно были введены слишком многие незнакомые конструкции Dart: именованные параметры, `Future/async/await`, `try/on/catch`, `implements`, factory-конструктор, switch expression, `map` с callback и runtime-приведение JSON. Это признано ошибкой темпа обучения. Дальнейший сетевой слой разбирается последовательно на текущем коде пользователя с Python-аналогами; новая конструкция не должна появляться без предварительного объяснения.

Первый пользовательский вариант сетевого кода архитектурно направлен верно (`ApiClient` и `CustomersRepository` разделены), но на момент проверки содержит известные технические ошибки: `baseUrl` без схемы `http://`, опечатку `Acept`, пропущенную точку с запятой после конструктора repository и несоответствие результата `map()` объявленному `Future<List<dynamic>>`. Файл `api/get_clients.dart` пока пуст по смыслу и дублирует ещё не определённую application-прослойку; решение о его роли не принято.

После исправлений `ApiClient` и `CustomersRepository.getCustomers()` признаны достаточными для первого получения списка клиентов: метод возвращает `Future<List<Customer>>`, преобразует JSON через `Customer.fromJson` и переводит `DioException` в прикладное сообщение. Пустой `api/get_clients.dart` удалён.

Уточнена граница frontend use case: отдельный класс use case не обязателен, если он только без изменений повторяет один метод repository и не содержит бизнес-правил, координации нескольких источников или переиспользуемого сценария. UI может получать данные через repository посредством своего слоя состояния/controller; на раннем экране допустимо вызвать repository из `State`, но нельзя выполнять сетевой запрос внутри `build()`, поскольку перестроение виджета запустит его повторно.

## Запись 2026-09-19 — отдельный mock backend

Пользователю нужен простой Python HTTP-сервер с синтетическими ответами, чтобы продолжать разработку без основного backend. Изменять Flutter-интерфейс без явного указания запрещено; начатые изменения клиента полностью отменены. Добавлен отдельный `mock_backend/` на FastAPI с данными в `data.py`, `GET /customers?limit=&offset=` и вспомогательным `GET /health`, на уже заданном в клиенте адресе `127.0.0.1:8000`. Хранилище и авторизация не имитируются.

Совместимость списка сверена с текущими Dart DTO, repository и тестом. Актуальный backend/OpenAPI по прежним путям недоступен; найденная папка `/home/zemphix/coding/crm` не содержит этих контрактов, `AGENTS.md` или `Diary.md`. Полное совпадение серверных ограничений и формата `/health` не подтверждено; синхронизация общих документов с backend остаётся до появления его актуальной копии.

## Запись 2026-09-19 — исправление данных mock по HTML-шаблону

Первый mock ответ ориентировался лишь на Dart DTO списка и пропустил нужные данные карточки. По `crm_template.html` заглушка теперь содержит три показанных клиента с телефонами, филиалами, ответственными, несколькими контактами, заметками, задачами и историей назначений. По решениям дневника отдельно представлены источник привлечения, реферер, способ регистрации и обращения; `last_interaction_at` вычисляется по истории обращений, а не по заметкам. Для полной карточки добавлен `GET /customers/{id}`, прежние поля списка сохранены. Форма нового HTTP-ответа остаётся предварительной: шаблон является визуальным ориентиром, а действующие схемы backend/OpenAPI недоступны. Flutter-код не изменялся.
