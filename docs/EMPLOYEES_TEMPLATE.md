# Мини-раздел сотрудников: интерактивный макет

Макет находится в `crm_template.html`: кнопка «…» под основными разделами →
«Сотрудники» → «Добавить сотрудника» / «Архивировать сотрудника».
Наведите мышь на «Сотрудники» либо нажмите этот пункт. Отдельный экран не открывается:
формы появляются поверх текущего раздела. Старые макеты HR и филиалов сохранены.

## Что изучено

Проверены официальные материалы и скриншоты интерфейсов:

- [HubSpot — создание пользователей](https://knowledge.hubspot.com/account-management/add-hubspot-users):
  отделение данных пользователя от прав, описание уровня доступа и проверка перед созданием.
- [Zoho CRM — пользователи, роли и профили](https://help.zoho.com/portal/en/kb/crm/security-control/data-security-types/articles/get-started-manage-users):
  роль и набор разрешений — разные понятия. В нашей модели выбирается готовая роль;
  дополнительная сущность «профиль», лицензии мест и матрица разрешений здесь не вводятся.
- [Bitrix24 — отключение сотрудника](https://helpdesk.bitrix24.com/open/25785571/):
  прекращение доступа с сохранением истории, подтверждение действия и объяснение последствий.
- [HubSpot — отключение и удаление](https://knowledge.hubspot.com/user-management/remove-hubspot-users):
  разделение этих действий; для некоторых опасных операций есть ручное подтверждение идентификатора.

Это ориентиры UX, а не копия продукта или его бизнес-правил. Наш компактный вход
через «…», ручной логин и снятие исполнителя с задач — требования пользователя.
Исследование выполнено 2026-10-13. Визуально просмотрен официальный скрин HubSpot
этапа проверки доступа; итоговый макет использует существующие цвета нашего шаблона.

## Сценарии

**Создание:** ФИО, уникальный логин, готовая роль с кратким описанием возможностей.
Филиалы необязательны, основной выбирается только среди отмеченных. Привилегированная
роль не выбрана по умолчанию. После создания появляется отдельный результат с логином
и замаскированным примером временного пароля: показать/скрыть, скопировать, закрыть.
Если буфер обмена недоступен, это явно сообщается, ложного «скопировано» нет.

**Архивирование:** только ручной ввод точного логина, без подсказок и списка.
«Продолжить» показывает ФИО, роль и число открытых задач; «Архивировать» подтверждает
действие. Смена ввода сбрасывает подтверждение. Аккаунт не удаляется: доступ
отключается, у открытых демонстрационных задач `responsibleId=null`, их статусы
сохраняются, версии увеличиваются, снятие назначений попадает в локальную историю.
Завершённые задачи и их прежние назначения остаются. Есть ошибки неизвестного
логина, повторного отключения, своего аккаунта, последнего администратора и версии.

Меню поддерживает мышь, нажатие/касание, стрелки, Escape и закрытие снаружи.
Диалоги используют нативный HTML `dialog`: модальность, фокус, Escape и прокрутка.
На узкой ширине подменю раскрывается внутри меню, диалоги остаются в пределах окна.

## Важные ограничения

Это только HTML-прототип, **не реализованная авторизация и не подтверждённый API**.
Роли, аккаунты, задачи и имитация отзыва сессий локальны; реальные права не проверяются.
Состояние мини-раздела независимо от старого HR/канбана, живёт только до перезагрузки
страницы. Старые макеты и их localStorage не меняются. Реальные backend/Flutter не тронуты.

Пример пароля создаётся в памяти браузера, не является рабочим credential,
не добавляется в данные аккаунта, localStorage или журнал и очищается при закрытии
результата. В продукте пароль выдаёт сервер, а не JavaScript.

Для реальной реализации нужны согласованный точный lookup логина, команда
отключения со снятием назначений, серверные права, транзакция/история/версии и отзыв
сессий. Старое правило backend с обязательным преемником нельзя обходить клиентом.
Описания ролей в макете — примеры, в продукте они должны соответствовать API.

## Перенос в Flutter (без API)

Формы перенесены в `lib/modules/employees/`; манифест регистрирует общий тип
модуля с действиями, `ModuleDefinition.menu`, вместо фиктивного экрана.
В меню «…» используется SDK SubmenuButton. При закреплении пункт открывает
MenuAnchor с теми же действиями. Текущий экран и его состояние не меняются.

В отличие от HTML, синтетические справочники/аккаунты в приложение не встроены.
Пока API выключен, поля ФИО/логина доступны, роли и филиалы пусты, отправка и
lookup отключены с пояснением. Результат создания и подтверждение архива
отделены от источника данных: их можно включить будущими обработчиками,
не переписывая формы. Тесты передают fixture-данные только внутри тестов.
Временный пароль Flutter не генерирует и не сохраняет; при наличии результата
показывает его замаскированно, копирует только по нажатию и очищает при закрытии.
При ожидании callback закрытие/повтор заблокированы, ошибки сохраняют ввод;
неопределённый исход можно отобразить без разрешения слепого повтора.
