# Архитектура и границы продукта

Записи перенесены 2026-09-19. Если Notes не указывает дату исходного решения, date означает дату его фиксации при миграции; точный день принятия неизвестен. Active означает действующее требование, а не гарантию реализации. Открытые вопросы внутри Notes не являются утверждёнными решениями.

## ARCH-01 — Выделенная CRM и границы MVP

date: 2026-09-19
status: active
tags: self-hosted, deployment, modules, b2c, b2b, deals

Decision:
- Система не является SaaS и не является общей multitenant-инсталляцией: для каждой компании разворачивается выделенное серверное окружение и отдельное хранилище данных. Обычно один backend обслуживает все филиалы компании через интернет, однако возможность нескольких backend-установок для одной компании пока не исключена и требует отдельного лицензионного контракта. Не добавляйте `organization_id` во все бизнес-таблицы для изоляции арендаторов.
- Компания работает с сервером через нативно компилируемый Flutter-клиент. Ранее созданный Flet-код является экспериментальным прототипом и не считается основой продуктового интерфейса. Любой клиент остаётся недоверенной стороной; сервер самостоятельно проверяет аутентификацию, права и входные данные независимо от отсутствия у заказчика административного доступа к серверу.
- Базовая CRM ориентирована на B2C — работу с физическими лицами. B2B для юридических лиц планируется отдельным подключаемым бизнес-модулем со своими сущностями, логикой, API и разделом интерфейса; не добавляйте B2B-поля и универсальную модель контрагента в базовую таблицу B2C-клиентов.
- Сделки, воронки и стадии продаж не входят в базовый прототип и планируются отдельным подключаемым модулем `deals`, поскольку этот процесс нужен не всем целевым компаниям. Базовые клиенты и задачи не должны зависеть от наличия `deals`; модуль сделок при подключении ссылается на их публичные идентификаторы и контракты.
- Аналитика планируется отдельным модулем. Базовые модули обязаны сохранять структурированные бизнес-факты, необходимые для достоверной аналитики; сам аналитический модуль не должен вынуждать их извлекать отчётные данные из неструктурированных технических логов или произвольного JSON общего аудита.

Reason:
Нужна минимальная CRM для разных компаний, в том числе малого бизнеса. Лояльность, B2B и сделки не должны диктовать устройство базовых клиентов.

Alternatives considered:
Расширение старого loyal-system; SaaS/multitenant; заранее универсальная сущность контрагента. Выбран отдельный проект базовой CRM.

Affected areas:
core/, application/, domain/, database/, web/; Flutter lib/modules/

Notes:
Backend и frontend — разные репозитории; backend остаётся модульным монолитом. DeepSeek Harness — лишь обсуждавшийся ориентир. История перехода Flet → Flutter: ../journal/2026-09.md (tags: flutter, flet).

## ARCH-02 — Встроенные официальные модули

date: 2026-09-19
status: active
tags: modules, licensing, flutter, packaging

Decision:
- [Правило размещения superseded: ARCH-05.] Пользовательская модель модулей ориентировалась на интерфейс VS Code: включённый модуль регистрирует отдельный пункт/иконку в левой навигации и открывает собственный раздел интерфейса. Ограничение реализации сохраняется: минимальный явный реестр встроенных модулей без динамической установки стороннего кода, marketplace или универсального plugin framework.
- Дополнительные модули приобретаются на всю компанию и включаются сотрудником поставщика через внутреннюю CRM. На текущем этапе код и интерфейсы всех официальных модулей заранее входят в общие сборки backend и Flutter-клиента, но неактивные или нелицензированные модули не регистрируются в доступной навигации и остаются недоступны через API. Backend обязан проверять лицензию независимо от скрытия элементов интерфейса. После отключения данные модуля сохраняются, но обычный доступ к ним блокируется. Если размер или сопровождение общей Flutter-сборки станет существенной проблемой, модель поставки пересматривается отдельно.

Reason:
Одна сборка упрощает установку и сопровождение; цену большого дистрибутива оценим по фактическим измерениям.

Alternatives considered:
Отдельные Python-пакеты, комбинации Flutter-сборок под клиента, загрузка модулей на лету. Рассматривались, но не выбраны для текущего этапа.

Affected areas:
core/; будущий реестр модулей; Flutter lib/layout/ и lib/modules/

Notes:
Публичный контракт модулей и внедрение дополнительных данных в карточки ещё открыты. Не превращать этот выбор в требование написать все модули до MVP. Неактивный модуль сохраняет данные.
ARCH-05 заменяет только правило обязательного размещения каждого модуля в сайдбаре;
модель общей сборки, лицензирования и сохранения данных остаётся active.

## ARCH-03 — Ядро, API и владение кодом

date: 2026-09-19
status: active
tags: core, common, boundaries, contracts

Decision:
Ядро содержит общесистемные контракты и инфраструктуру. Модули взаимодействуют через публичные API/контракты/события; зависимости явные, без циклов. Клиент обращается только к API, не к БД. Общий код выносится при подтверждённом одинаковом смысле у нескольких потребителей.

Reason:
Не повторять тесную связь CRM с лояльностью из старого проекта; отключение модуля не должно ломать независимые области.

Alternatives considered:
Общая папка common/utils для всего кода и ранний универсальный plugin framework не приняты.

Affected areas:
core/, domain/, application/, database/, web/; frontend lib/core/

Notes:
Фактическая раскладка backend пока послойная, не переводить весь код в modules одним несвязанным рефакторингом.

## ARCH-04 — Навигация: сотрудники и филиалы как сущности, аналитика и каталог как модули

date: 2026-09-27
status: active
tags: navigation, modules, employees, branches, analytics, catalog

Decision:
Сотрудники и филиалы остаются сущностями CRM, но не занимают собственные пункты-модули в левой навигации. Вместо них в навигации проектируются «Аналитика» и «Каталог». Внутри аналитики первый экран называется «Дашборды»; каталог представлен отдельным экраном HTML-прототипа (детали — FE-07). Существующие макеты сотрудников и филиалов в HTML не удаляются.

Reason:
Навигация должна отражать самостоятельные продуктовые области, а не каждую важную сущность данных.

Alternatives considered:
Сохранить отдельные навигационные модули филиалов и сотрудников; назвать весь аналитический модуль «Дашборды», что сузило бы его возможный состав.

Affected areas:
crm_template.html; будущая навигация Flutter и границы модулей.

Notes:
Это решение о продуктовой навигации, не об удалении таблиц, ORM-моделей или API сотрудников и филиалов. Конкретное размещение экранов управления этими сущностями ещё не определено. HTML-прототип не подтверждает включение аналитики/каталога в MVP или лицензию: правила доступности определяются отдельно согласно ARCH-02.
Размещение каталога как обязательного основного пункта superseded: ARCH-05.
Сотрудники, филиалы и базовый каталог планируются в дополнительном меню.

## ARCH-05 — Базовые и расширенные возможности, настраиваемая навигация

date: 2026-10-10
status: active
tags: modules, navigation, sidebar, overflow-menu, catalog, employees, branches, capabilities

Decision:
Базовые сотрудники, филиалы и каталог доступны через дополнительное всплывающее
меню по кнопке-стрелке («трей» в пользовательской терминологии). Это группировка
разделов, а не механизм фоновых процессов или новый класс плагинов.
Подключение расширенных возможностей даёт один раздел с базовыми функциями
и дополнениями, а не две параллельные версии в разных меню. Данные сохраняются;
повышение уровня не является переносом или дублированием сущностей.
Пользователь может через ПКМ убрать раздел из основной панели в дополнительное
меню и обратно закрепить его в панели, по аналогии с VS Code. Раздел представлен
в одном месте; закрепление не включает модуль, не расширяет функции и не меняет
лицензию или права. Доступность продолжает проверяться сервером.

Reason:
Самостоятельная ценность базового каталога не оправдывает обязательную основную
иконку. Пользователь хочет доступ к вспомогательным разделам без перегруженной
панели и без дублирования при подключении расширений.

Alternatives considered:
Две независимые базовая/полная версии с двумя пунктами; обязательное размещение
всех включённых модулей в основной панели; встраивание продаж в каталог ради
повышения его самостоятельной полезности. Эти варианты не выбраны.

Affected areas:
Будущая навигация Flutter lib/layout/; разделы сотрудников, филиалов и каталога;
отображение доступных возможностей. Контракты расширений проектируются отдельно.

Notes:
Уточняет ARCH-02 (только прежнее размещение каждого модуля в сайдбаре) и ARCH-04
(каталог как обязательный основной пункт); заменённые части помечены superseded
в исходных записях. Разделение ответственности ARCH-03 сохраняется: продажи,
склад и лояльность не переносятся в каталог. UI пока не реализован. Хранение
предпочтений закрепления, управление по клавиатуре и подробные UX правила
отдельно не согласованы. Backend этим решением не изменяется.

## ARCH-06 — Генерация реестра встроенных Flutter-разделов

date: 2026-10-10
status: active
tags: modules, manifest, codegen, registry, flutter, dart, composition-root

Decision:
По явному запросу пользователя реестр генерируется до сборки из прямых
lib/modules/*/module.dart. Каждая точка входа экспортирует
ModuleDefinition createModule(ApiClient apiClient): метаданные, стабильный ID,
иконка, порядок и WidgetBuilder. Фабрика сама собирает зависимости своего модуля;
общий контракт core/modules не импортирует прикладные области.
Генератор на Dart SDK создаёт lib/bootstrap/modules.g.dart — composition root
с импортами и вызовами фабрик. Файл хранится в Git; --check проверяет актуальность
без записи. Пути детерминированы, symlink не обходятся, негенерированный файл
не перезаписывается. Типы фабрик проверяет анализатор/компилятор; ID, их уникальность
и название проверяет неизменяемый ModuleRegistry. Навигация читает этот реестр,
без AppScreen enum, switch и отдельных списков кнопок в sidebar.
Генерация запускается перед F5 через VS Code preLaunchTask и перед командами
run/build/test через dart run tool/flutter.dart. Прямой Flutter CLI не перехвачен:
перед ним разработчик сам запускает генерацию. Экраны создаются при выборе раздела,
не при регистрации; смена раздела сохраняет прежнюю политику уничтожения State.

Reason:
Добавление модуля не должно требовать синхронных правок enum, сайдбара и AppShell.
Пользователь выбрал автоматическое обнаружение исходников при сборке вместо
ручного поддержания общего списка импортов.

Alternatives considered:
Ручной реестр — меньше инструментов, но сохраняет повторяемый ручной шаг.
Стандартный build_runner проверен: полезен для общего графа генераторов/watch,
но здесь добавил бы зависимости без устранения специфичного контракта реестра.
Выбран небольшой SDK-only генератор с фиксированным соглашением о точках входа,
без regex-парсинга Dart, reflection, динамических импортов и runtime-плагинов.

Affected areas:
lib/core/modules/; lib/bootstrap/; lib/modules/*/module.dart; lib/layout/;
lib/main.dart; tool/; .vscode/; test/module_*_test.dart; README.md.

Notes:
Реализует минимальный реестр из ARCH-02, не отменяет модульные границы ARCH-03.
ARCH-05 (дополнительное меню/закрепление) пока не реализован. Реестр содержит
прежние четыре раздела; аналитика/каталог остаются заглушками. Backend, лицензии,
получение активных модулей и серверные права этим этапом не изменены.
Новые модули требуют генерации и restart; произвольный Dart-код из установленного
приложения не загружается. Расширенный lifecycle/контракты зависимостей пока не нужны.
