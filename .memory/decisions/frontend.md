## FE-02 — Dio и repository без обязательного frontend use case

date: 2026-09-19
status: active
tags: dio, http, repository, futurebuilder, json, dto

Decision:
Один общий настроенный Dio/ApiClient передаётся repositories модулей. Repository знает endpoint и преобразует JSON в DTO. Для простого чтения допустим вызов repository из слоя состояния без класса-посредника, который только повторяет вызов.

Reason:
Готовый сетевой клиент уменьшает собственный код таймаутов, перехватчиков, ошибок и отмены. Простой frontend-сценарий не требует повторения backend-слоёв.

Alternatives considered:
package:http признан достаточным технически; выбран Dio. Пустой GetClients удалён.

Affected areas:
lib/core/api_client/client.dart; lib/modules/customers/repos/; lib/modules/customers/models/

Notes:
getCustomers возвращает Future<List<Customer>>; FutureBuilder отображает ожидание/ошибку, ListView — данные. Отдельный слой состояния/controller — направление; сейчас State создаёт ApiClient, управление временем жизни общего клиента ещё не доведено.

## FE-04 — HTTP-контракт и независимая работа над UI

date: 2026-09-19
status: active
tags: mock, openapi, http, websocket, refresh

Decision:
- Flutter-клиент не работает автономно без backend. Мгновенная синхронизация через WebSocket не входит в текущий план: после пользовательских операций клиент повторно получает актуальные данные обычным HTTP-запросом.
Flutter можно разрабатывать через отдельный mock, повторяющий согласованные схемы/OpenAPI, ошибки и пагинацию. Первый список использует реальный GET /customers с демо-клиентами.

Reason:
Не нужно ждать весь backend ради интерфейса; один контракт предотвращает расхождение mock и production.

Alternatives considered:
WebSocket для всех изменений сразу и production-запуск фиктивных данных не выбраны.

Affected areas:
web/api/customers/; Flutter repositories; отдельные dev mock/seed средства

Notes:
Mock допустим, но отдельный mock-сервер ещё не создан. HTTP-повтор после собственных операций не означает мгновенное получение изменений другого сотрудника.

## FE-05 — Канбан задач в HTML-прототипе

date: 2026-09-27
status: active
tags: tasks, kanban, subtasks, progress, drag-drop, template

Decision:
В `crm_template.html` вместо двух фиксированных блоков задач показывается канбан: пользователь может добавлять, переименовывать и удалять колонки; создавать и редактировать задачи с важностью, подзадачами, необязательным исполнителем, сроком и выбранной колонкой; отмечать подзадачи, видеть прогресс и переносить карточки между колонками.

Reason:
Прежние «Общая очередь / Мои задачи» не показывали полноценный рабочий сценарий управления задачами.

Alternatives considered:
Сохранить два фиксированных блока задач.

Affected areas:
crm_template.html; будущий модуль задач Flutter и его API-контракт.

Notes:
Это подтверждённое направление UI-прототипа, не утверждение схемы БД и не реализация backend/Flutter. Пользовательские колонки пока нельзя автоматически приравнивать к статусам жизненного цикла задачи из DB-решений; соответствие, порядок колонок, права на их изменение и правила переходов требуют отдельного проектирования. Данные HTML-прототипа сохраняются только в localStorage браузера.

Уточнение 2026-10-06: Flutter-форма показывает все колонки и отправляет выбранный `column_id` без фильтра по `new` и без подмены выбора. Пользователь явно отклонил введённое при адаптации ограничение формы. Текущий backend разрешает создание только в `new`; это остаётся расхождением для согласования с его разработчиком, не основанием снова ограничивать UI по собственной инициативе.

Проверка 2026-10-07, backend 0656dc5: прежнее ограничение «только new» снято. Наблюдаемый API разрешает остальные незакрытые статусы с tasks.move, исполнителем для in_progress/completed и reason для rework; confirmed/cancelled запрещены. Это технический контракт обновления, не новое согласованное ограничение Flutter-формы: её выбор не менялся, reason ещё не добавлен. Nullable customer_id/срок и описание в GET доски теперь поддержаны сервером.

Уточнение 2026-10-07 по явному поручению адаптировать frontend к реальному контракту:
форма колонки отправляет name и выбранный status; форма задачи сохраняет выбранную
незакрытую колонку, проверяет исполнителя для in_progress/completed и reason для
rework. Закрытые и неизвестные статусы видны, но недоступны для создания; это
заменяет прежнюю техническую заметку о непроверяемом выборе всех статусов, а не
возвращает отклонённое ограничение «только new». Проверки UI не заменяют серверные
права. Ошибки 4xx показываются без потери ввода, внутренние ошибки 5xx не раскрываются.

Уточнение 2026-10-07: по требованию исправить неработающее меню Flutter подключены
PATCH /task-columns/{id} с name/version и DELETE с query move_to_column_id.
Реальный API архивирует, а не физически удаляет колонку; запрещает архивирование
последней колонки статуса и разрешает перенос только в колонку того же статуса.
UI честно показывает эти ограничения; произвольный перенос из HTML-прототипа
не переносится в серверный контракт. Drag-and-drop остаётся AppFlowy, отдельный
CustomPainter отвечает только за рамки/фон и пунктир, не за бизнес-логику.

## FE-06 — Первый дашборд аналитики

date: 2026-09-27
status: active
tags: analytics, dashboards, profit, calendar-periods, custom-charts, template

Decision:
Первый экран модуля «Аналитика» — дашборд с графиком «Прибыль». Календарные интервалы: неделя (по дням), текущий/выбранный месяц (по дням), год (по месяцам), всё время (по неделям, не более 52 столбцов; при длинной истории шаг увеличивается до 2, 4 и более недель). Неделю, месяц и год можно листать назад/вперёд. График компактный; при наведении, фокусе или выборе значение и отрезок показываются подсказкой непосредственно над столбцом, а не в отдельном блоке. Кнопка «Добавить график» содержит название, описание, метрики X/Y и тип графика.

Reason:
Пользователю нужен читаемый обзор во времени и направление для будущих пользовательских отчётов, вместо пустой вкладки аналитики.

Alternatives considered:
Сразу строить все аналитические метрики и серверный конструктор отчётов; отложено до определения источников данных и семантики метрик.

Affected areas:
crm_template.html; будущий модуль аналитики Flutter и его API.

Notes:
HTML показывает только явно помеченные демоданные «прибыли». Значение прибыли, финансовые источники, набор метрик X/Y и серверный контракт ещё не определены. Пользовательские графики в прототипе сохраняются как черновики конфигурации в localStorage и пока не визуализируют данные. «Всё время» не имеет соседнего периода для листания, поэтому стрелки для него отключены. Компоновка обзора: график слева на половину ширины, справа карточки 2×2 (прибыль за всё время, прибыль за период, выполнено задач, активные задачи). В HTML счётчики задач временно опираются на демоколонку с ID `done`; это не утверждённая доменная модель статусов задач. Не переносить демоформулу или эту привязку колонки в backend как бизнес-расчёт.

## FE-08 — Одна задача в канбане и карточке клиента

date: 2026-10-08
status: active
tags: tasks, customers, customer_id, autocomplete, linking, pagination

Decision:
Связь задачи с клиентом необязательна. Одна серверная запись задачи отображается
на канбане и во вкладке клиента по GET /tasks?customer_id, с учётом серверных
прав/фильтров. Не создавать отдельные клиентские копии задач. Из канбана клиент
выбирается через API-поиск, из карточки — та же форма получает закреплённого
клиента. Редактирование позволяет заменить/снять связь; отсутствие customer_id
в PATCH сохраняет её, explicit null отвязывает. Отображаемое имя клиента берётся
из серверного ответа, введённый текст сам по себе не становится привязкой.

Reason:
Пользователь поручил завершить привязку задач к клиентам после принятия
задачника для текущего этапа. Нужны внутренние задачи без клиентов и удобное
создание клиентских задач без повторного поиска карточки. API уже поддерживает
nullable customer_id и фильтрацию. Предыдущий пункт DB-04 «всегда клиентская
задача» superseded этим решением; остальные правила DB-04 здесь не пересматриваются.

Alternatives considered:
Раздельные записи задач для клиента/канбана, обязательная привязка и загрузка
всех клиентов в один dropdown не выбраны. Используется встроенный Autocomplete
с асинхронным API-поиском и debounce; новых зависимостей нет.

Affected areas:
modules/tasks/models, repos, widgets, screens; customers DetailPanel

Notes:
Клиентская вкладка пагинирована; после создания/правок данные обновляются.
Автосинхронизация и обзор «Ближайшее взаимодействие» не входят в эту реализацию.
Позднее обзор подключён в FE-09; исключение относится только к исходному этапу FE-08.
Список канбана может отличаться по фильтрам/окну закрытых задач. Изменение прав
не эмулируется клиентом. Старый mock не адаптирован к новому сценарию.

## FE-09 — Реальная ближайшая задача в обзоре клиента

date: 2026-10-08
status: active
tags: customers, tasks, closest-task, deadline, completion, pagination

Decision:
Обзор вместо заглушки показывает первую доступную задачу клиента в статусе
new/in_progress/rework по серверной сортировке due_at с nulls last и ID tie-breaker.
Просроченные включаются; completed (ожидает подтверждения), confirmed и cancelled
не считаются предстоящей работой. Если первая страница занята ими, чтение
продолжается до кандидата или конца списка. Без срока кандидат тоже отображается.
Календарный due_date не сдвигается часовым поясом, due_at показывается локально.
«Выполнено» использует существующий POST status из in_progress; сервер проверяет
права исполнителя. Новая задача/доработка не перескакивают переход в работу:
назначенному исполнителю предлагается «В работу» через тот же POST status с
in_progress, затем «Выполнено». Без исполнителя начало отключено с подсказкой;
само назначение статус не меняет. Клиент не знает ID текущего сотрудника в этом
виджете: кнопка доступна при наличии исполнителя, принадлежность проверяет сервер.

Reason:
Пользователь сообщил: привязка работает в задачнике, но ближайшая задача клиента
не отображается. Причина — overview передавал null вместо реальной DTO.
Нужен рабочий обзор, а не новая сущность взаимодействия или клиентская копия задачи.

Alternatives considered:
Не выбран поиск только по первой странице, объединение задачи с историей визитов,
локальное фиктивное завершение или новая зависимость управления состоянием.
Использованы уже существующий репозиторий задач и стандартные StatefulWidget.

Affected areas:
modules/tasks/repos/tasks.dart, widgets/customer_next_task.dart,
widgets/customer_tasks.dart, customers/widgets/customer_details

Notes:
Обновление при создании/изменении в карточке и вручную; общей realtime-системы нет.
Отдельный mock не адаптирован, backend не менялся. Расширяет FE-08, а не заменяет
решение единой записи задачи. Серверная сортировка и доступность обязательны.

## FE-10 — Серверное сохранение переноса и согласованность представлений

date: 2026-10-08
status: active
tags: tasks, drag-drop, move, version, consistency, rollback, stale-response

Decision:
Drag-and-drop между колонками вызывает POST /tasks/{id}/move с column_id/version
и обязательной для некоторых переходов причиной. После ответа UI использует
серверные column_id/status/version, а не визуальное положение/название колонки.
В ожидании блокируются действия доски. При отказе восстанавливается исходная DTO
и перечитывается доска, чтобы учесть конфликт версии/неопределённый исход запроса.
Отмена причины возвращает карточку без POST. Поздний GET не затирает новую мутацию.

Reason:
Пользователь увидел «Выполнено» в клиенте после визуального возврата в новые.
Действительный статус оставался in_progress: обработчик переноса только печатал
debug-сообщение. Это не проблема кеша клиента, а несохранённая мутация доски.
Пользователь попросил учитывать аналогичные расхождения в дальнейшей разработке.

Alternatives considered:
Не выбраны подмена статуса только в памяти, обход серверных переходов, новый
event bus/state framework или backend-изменения без отдельного поручения.
Использован callback установленного AppFlowy и штатный API; новый клиентский
запрос при возврате из задач к клиентам уже обеспечен текущим AppShell.

Affected areas:
modules/tasks/models/tasks.dart, repos/tasks.dart, screens/tasks.dart,
widgets/move_task_reason.dart; AGENTS.md

Notes:
Backend read-only: in_progress → new запрещён даже с tasks.move. Это существующее
ограничение, не вновь принятое бизнес-правило. UI сообщает отказ и не создаёт
иллюзию успешного возврата. Его изменение обсуждать с владельцем backend.
Внутриколоночный порядок/порядок колонок и realtime между устройствами не добавлены.
Для последующих мутаций: API → подтверждённая DTO → обновление/инвалидация всех
затронутых представлений, с проверкой отказов, версий и устаревших GET.

## FE-11 — Заметки клиента: типизированный контракт и состояние карточки

date: 2026-10-08
status: active
tags: customers, notes, tabs, version, archive, conflict, draft, stale-response

Decision:
Заметки принадлежат модулю клиентов, модель CustomerNote и запросы типизированы.
Чтение использует notes из GET /customers/{id}, без выдуманного GET /notes.
POST передаёт text, PATCH — text/version, DELETE архивирует после 204.
Список хранится в DetailPanel, вкладка сообщает изменения callback-ом: удаление
дерева таба не возвращает старые данные FutureBuilder. Другой клиент сбрасывает
список, поздний ответ прежнего клиента игнорируется. Создание — inline SDK Form,
правка/архивирование — SDK AlertDialog; карточки заметок не заменять timeline.

Reason:
Пользователь поручил реализовать заметки следующим этапом после задач клиента.
Сервер уже имеет контракт и проверки авторства; локальная имитация успеха и
сброс записей при переходах между табами нарушили бы согласованность.

Alternatives considered:
Не выбраны сырой Map вместо модели, хранение только внутри исчезающей вкладки,
новая библиотека состояния, отдельный GET без подтверждённого API, автоматический
повтор POST/перезапись после конфликта или смешение заметок с полной историей.

## FE-12 — Независимые колонки, активность клиента и история задачи

date: 2026-10-08
status: active
tags: neutral-column, optional-status, customer-activity, column-history, pagination

Decision:
По поручению пользователя frontend адаптирован к подтверждённому API 4e5b63a.

ответы. Это не realtime или общий audit log; actor=null допустим, note data={}.
История задачи по меню запрашивает детали один раз и показывает status_history,
assignment_history и column_history. Чистое перемещение не выдумывать в ленте клиента.

Reason:
Пользователь подтвердил новые возможности backend и поручил подключить их к UI.
Колонка и состояние задачи теперь независимы; старый String/canCreateTask ломали
нейтральный сценарий. Для истории и ленты уже есть реальные API-контракты.

Alternatives considered:
Не выбраны угадывание состояния по названию колонки, обход lifecycle,
автоматическая смена статуса, запрос истории для каждой карточки, новая библиотека
состояния или синтетические события/тексты заметок внутри клиента.
Использованы SDK Form/DropdownButtonFormField/ListView/AlertDialog и существующий Dio.

Affected areas:
modules/tasks/{models,repos,screens,widgets}; modules/customers/{models,repos,
widgets/customer_details}; тесты activity/history/columns/move.

Notes:
FE-10 остаётся активным: только подтверждённые DTO/версии меняют UI.
DB-04/TASK-WORKFLOW-001 не заменены: обратные переходы остаются серверной политикой.
Отдельная клиентская вкладка «История» не подключена, mock не адаптирован,
