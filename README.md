# crm_interface

Flutter-клиент модульной CRM для Windows.

## Локальный запуск

В Windows-терминале из корня проекта:

```powershell
flutter pub get
flutter run -d windows
```

API-клиент использует `http://127.0.0.1:8000`. Реальный backend запускается в
своём репозитории; его PostgreSQL и миграции должны быть подготовлены отдельно.
Проверка доступности — `GET /health`; для бизнес-ручек требуется вход сотрудника.
Для независимой разработки интерфейса есть [mock_backend](mock_backend/README.md).
Реальный и mock-сервер нельзя одновременно запускать на одном порту.
Windows SDK запускайте из Windows, не как Linux-shell скрипт в WSL.

В Windows runner добавлена защита от невидимого режима меню после Alt/Alt+Shift,
который может поглощать следующий символ во всех текстовых полях. Она действует
только для окна без нативной строки меню; Alt+Space и другие системные команды
сохраняются. После изменения `windows/runner/*.cpp` полностью остановите
приложение и запустите `flutter run -d windows`: hot reload/hot restart
не пересобирают нативную часть. Ручная проверка раскладки: [.memory/bugs.md](.memory/bugs.md).

## Карточка клиента

Ответственный и автор регистрации читаются из вложенных `responsible` и
`created_by` в ответе API. Отдельных запросов сотрудников на каждую карточку нет.
Для предпочитаемого филиала подробная карточка загружает `GET /branches`:
показывает название, а при недоступности справочника/отсутствии записи — ID с
пояснением. Загрузка филиалов не блокирует остальные сведения клиента.
Отсутствие ответственного обозначается «Не назначен», отсутствие предпочтения
филиала — «Не выбран», а не фиктивными значениями.

В заголовке показаны реальные даты «В системе с» и «Карточка обновлена».
В обзоре — ближайшая задача и три последних события из
`GET /customers/{id}/activity?limit=3`. События системы и время правки карточки
не выдаются за посещение или контакт с клиентом. API пока не возвращает дату
последнего визита/взаимодействия: соответствующие заглушки и ложная отметка
«Нет визитов» в маленькой карточке убраны до появления подтверждённого контракта.
В маленькой карточке отображается имя ответственного, без `н/д` и запросов филиала.

Есть отдельное обновление всей карточки; обновление карточки перечитывает
также филиалы, заметки, задачи и активность. Ошибку получения событий можно
повторить отдельно, она не маскируется пустой историей. Обзор прокручивается;
на узкой панели его колонки располагаются друг под другом. Самостоятельная
история посещений, редактирование клиента/контактов и звонки здесь не реализованы.

Справа от вкладок одна кнопка «Обновить вкладку», без отдельных иконок в блоках.
Она обновляет только выбранное представление: обзор (карточка/филиалы, ближайшая
задача и последние события), активность, заметки либо задачи. Фильтр активности
и текущая страница сохраняются. У истории посещений кнопка отключена до появления API.
Во время загрузки/сохранения, открытых форм и изменения подзадач обновление
заблокировано; повторные запросы не пересекаются. Полное обновление карточки
сохранено отдельно. Ни оно, ни обновление вкладки не сбрасывает выбранный таб
и несохранённый черновик заметки; черновик также сохраняется между вкладками.

## Заметки клиента

Вкладка «Заметки» показывает текст, автора, дату создания и дату правки.
Есть добавление, редактирование, подтверждаемое архивирование и ручное обновление.
Создание — поле прямо во вкладке с одной кнопкой «Сохранить» цвета ActiveElement,
без дублирующей кнопки добавления, отмены и заголовка со счётчиком.
Заметки остаются отдельными карточками с автором и датами; лента с точками
используется только для активности. Правка и архивирование — из меню записи.
Первый список уже приходит в `GET /customers/{id}`; отдельного GET списка заметок
нет. Обновление перечитывает карточку. Создание — POST `/customers/{id}/notes`
с `text`; редактирование — PATCH `/customers/{id}/notes/{note_id}` с `text` и
текущей `version`; архивирование — DELETE этого же ресурса, ответ 204.
Автор и время назначаются сервером. Изменения отображаются по подтверждённому
ответу, не заранее; состояние списка хранится в карточке и не теряется при
переключении табов. При смене клиента старый ответ не меняет новую карточку.

Текст обязателен, до 4000 символов. Редактировать может только автор;
архивировать чужие записи — модератор. Сервер проверяет права независимо от UI,
при отказе данные остаются без изменений, форма сохраняет черновик.
При конфликте версии или неопределённом результате сохранение блокируется:
для добавления обновите заметки — черновик останется в поле. В диалоге правки
скопируйте черновик, закройте форму и обновите заметки перед повторной попыткой.
Автоматического перезаписывания чужой правки или повторного POST нет.
Заметки — рабочий контекст CRM, не медицинская карта. Архив и версии остаются
на сервере; просмотр ревизий и общая вкладка истории в этот этап не входят.
Для этого сценария используйте реальный backend: старый mock не адаптирован.

## Активность клиента и история задачи

«Активность» получает `GET /customers/{id}/activity`: события задач, заметок и
смены ответственного, от новых к старым, по 20 записей. Есть фильтр типа события,
пагинация, обновление и повтор после ошибки. Автор может быть неизвестен;
время отображается локально. События заметок не содержат текст — это ограничение
контракта, а не потеря данных интерфейсом. Сервер фильтрует события по правам.
Изменения заметок/задач в карточке инвалидируют ленту; realtime не добавлен.
Поздний ответ прежнего клиента/фильтра не заменяет актуальные данные.

Меню карточки задачи на канбане и у клиента содержит «История задачи»:
один `GET /tasks/{id}` при открытии, без дополнительных запросов на каждую карточку.
Диалог показывает историю колонок, статусов и назначений, автора, время и причину.
Чистое перемещение между колонками видно здесь, но не в ленте клиента.
Вкладка «История посещений» предназначена для реальных посещений клиента,
но пока явно сообщает об отсутствии API. Смены ответственного остаются в активности;
это новое продуктовое решение заменяет назначение вкладки истории в HTML-шаблоне.
Не выводите отсутствие визитов из отсутствия API или из активности задач.
Кнопки «+ Задача»/«Позвонить» повторяют состояния наведения шаблона;
«Позвонить» сообщает, что звонки ещё не подключены. Если ближайшей задачи нет,
кнопка завершения не отображается.
Для новых сценариев нужен backend с миграциями коммита `4e5b63a`;
старый mock их не поддерживает. Миграции и запуск backend выполняются отдельно.

## Создание клиента

Поиск в панели «Клиенты» выполняется сервером по имени, телефону или email,
не ограничивается уже загруженными карточками. После ввода есть задержка 300 мс;
Enter запускает запрос сразу, крестик очищает поиск и возвращает общий список.
Строка ограничена 100 символами по backend-контракту. Устаревшие ответы не
заменяют результаты нового запроса. При ошибке «Повторить» сохраняет поиск;
создание клиента также перечитывает список с текущим запросом. Выбранная
подробная карточка не закрывается из-за изменения поиска. Пагинация панели
и кнопки фильтров пока не подключены; сохраняется прежний лимит списка 50.
Фильтры выровнены слева. Отдельной кнопки обновления списка нет: Enter повторяет
текущий поисковый запрос, очистка поиска возвращает общий список; переход из
модуля и обратно также пересоздаёт запрос. Ошибки по-прежнему имеют «Повторить».

Кнопка «+» в панели «Клиенты» открывает форму: ФИО, дата рождения,
телефон и/или email, пол, источник привлечения, необязательные предпочитаемый
филиал и ответственный сотрудник. ФИО, дата рождения, источник и хотя бы один
из двух контактов обязательны по действующему backend-контракту. Телефон вводится
с `+` и кодом страны. Дату можно ввести как `дд.мм.гггг` или выбрать в календаре;
в API отправляется календарная дата `YYYY-MM-DD` без часового пояса.

Справочники загружаются из `GET /acquisition-sources`, `/branches`, `/employees`.
Без доступного источника форма не подставляет фиктивный ID. `POST /customers`
отправляет типизированную DTO в JSON; сервер определяет автора/способ регистрации
и независимо проверяет данные и права (`customers.read` + `customers.create`).
После успеха диалог закрывается и список перечитывается. Ошибки не очищают ввод;
повторная отправка и закрытие во время сохранения заблокированы. Если обновление
списка не удалось, «Повторить» повторяет только GET, а не создание клиента.

Форма сейчас создаёт основные телефон/email; дополнительные контакты и выбор
клиента-реферера в неё не включены. Используйте реальный backend: отдельный старый
mock-сервер ещё не реализует создание клиентов и эти справочники.

## Текущий канбан

Ширина колонок — 250 px; карточки занимают доступную ширину внутри них.
На узких карточках приоритет расположен под заголовком, а прогресс — отдельной
строкой. Полные обрезанные названия и метаданные доступны по наведению.

Задача может быть связана с клиентом или оставаться внутренней. В форме создания
и меню «Редактировать задачу» есть поиск клиента по имени/контакту через API;
выбор обязателен только если поле заполнено. Пустое поле означает отсутствие
привязки, а не автоматический выбор клиента. В редактировании можно поменять
клиента или снять привязку; неизменённая связь не перезаписывается PATCH-запросом.
На карточке канбана отображается имя связанного клиента.

В карточке клиента «+ Задача» открывает ту же форму с закреплённым клиентом.
Вкладка «Задачи» получает `GET /tasks?customer_id=...` с пагинацией, повтором
при ошибке и кнопкой обновления; это те же серверные записи, что на канбане,
не копии. В клиентском списке карточки компактные: название и описание по одной
строке (полный текст по наведению), статус/исполнитель/срок/прогресс рядом,
подзадачи раскрываются по нажатию. Без подзадач пустая шкала не показывается;
повторное имя клиента не занимает отдельную строку. Меню действий — справа
от названия. На узкой панели метаданные переносятся, а не выходят за границы.
Обычные карточки канбана сохраняют прежний вид.
После создания список клиента обновляется. Во вкладке доступны
прежние меню редактирования/назначения и отметки подзадач. При смене привязки
задача исчезает из списка прежнего клиента после сохранения. Права и
доступность по филиалам определяет сервер; мгновенная синхронизация между
открытыми представлениями не добавлена. Обзор «Ближайшая задача» получает
незавершённые задачи клиента, выбирая первую по серверной сортировке срока:
просроченные не скрываются, без срока идут последними. Статусы `completed`,
`confirmed` и `cancelled` исключены из обзора; если они занимают первую страницу,
поиск продолжает читать следующие страницы, а не показывает ложное отсутствие.
Показываются название, срок, статус и исполнитель. Календарный `due_date`
отображается без пересчёта зоны, точный `due_at` — в местном времени приложения.
После создания/правок в карточке обзор обновляется; есть ручное обновление и
повтор при ошибке. «Выполнено» отправляет POST `/tasks/{id}/status` с
`{"status":"completed"}` только для `in_progress`, после успеха перечитывает
ближайшую задачу и обновляет вкладку. Право исполнителя проверяет сервер;
отказ не меняет задачу локально. Для назначенной новой задачи или доработки
эта же кнопка показывает «В работу» и отправляет `{"status":"in_progress"}`;
после успеха становится «Выполнено». Без исполнителя начало работы недоступно,
подсказка предлагает назначить его в задачнике. Назначение само по себе статус
не меняет. Оба перехода проверяются сервером, автоматического обхода этапов нет.
Для нового сценария используйте реальный backend;
старый mock не адаптирован к поиску/пагинированному списку задач клиента.

Отложенные улучшения, включая локальный предварительный поиск и кеш повторных
запросов, записаны в [.memory/backlog.md](.memory/backlog.md).

Чтение доски, создание задач и колонок адаптированы к контракту backend 4e5b63a.
Форма колонки по умолчанию передаёт `status: null` — колонка только группирует
задачи и не меняет их статусы. Можно выбрать системный статус; после создания
изменить настройку нельзя (API поддерживает переименование, не смену статуса).
В нейтральной колонке новая задача получает `new`, не требует исполнителя/причины.
На карточках канбана показывается фактический статус задачи.
Задача может быть без клиента/срока;
для `in_progress` и `completed` нужен исполнитель, для `rework` — причина.
Вне `new` сервер требует `tasks.move`; создание в `confirmed`/`cancelled`
запрещено. Проверки формы служат удобству, сервер остаётся источником правил.
Ошибки 4xx отображаются в форме без очистки введённых данных.

Меню «…» колонки позволяет переименовать её (PATCH с `version`) или архивировать
(DELETE). Последнюю колонку каждого статуса архивировать нельзя; оставшиеся задачи
переносятся в выбранную нейтральную колонку или колонку того же статуса.
Для нейтрального источника совместимость статусов с выбранной целью проверяет
сервер: смешанные статусы можно переносить только в нейтральную колонку.
Пустую нейтральную колонку можно архивировать без цели; при конкурентном появлении
задач сервер отклонит команду. Серверные ошибки показываются
в диалоге без потери ввода. После архивирования доска запрашивается заново.
Эти команды подключены к реальному API; старые PATCH/DELETE mock-сервера ещё
не адаптированы к этому контракту.

Внизу доски есть горизонтальный скроллбар. На карточках с подзадачами раскрывается
чеклист: отметка отправляет PATCH `/tasks/{id}/subtasks/{subtask_id}` с `done`
и текущей `version` задачи. Галочка и прогресс берутся из ответа сервера; повторные
нажатия во время запроса заблокированы. Сервер проверяет права автора/исполнителя
и состояние задачи. Старый mock-контракт этой команды отдельно не адаптирован.

Меню «…» справа от прогресса карточки открывает редактирование названия,
описания и важности (PATCH с `version`) или назначение/снятие ответственного
(POST `/tasks/{id}/assign`, необязательная причина). Остальные данные задачи
не затираются. Пункт «Удалить задачу» отключён с пояснением: в текущем реальном
API нет удаления/архивирования задач. Чеклист подзадач компактный, с подписью
«Подзадачи · выполнено/всего»; раскрытие сохраняется при обновлении карточки.

Перетаскивание между колонками сохраняется через POST `/tasks/{id}/move`
с `column_id`, текущей `version` и, когда требуется, `reason`. Положение, статус
и новая версия берутся из ответа, а не угадываются по названию колонки.
Пока запрос выполняется, действия доски заблокированы и показан индикатор.
При отказе карточка возвращается, серверные данные перечитываются; если повторное
чтение тоже не удалось, остаётся прежнее положение и отображается ошибка.
Переход на доработку/закрытие требует причины, отмена диалога отменяет перенос.
Текущий backend запрещает `in_progress → new`: такой перенос отклоняется,
в том числе при наличии прав на перемещение. Изменение этого правила требует
отдельного согласования с разработчиком backend. Возврат к клиентам открывает
новый экран с новым запросом, поэтому он получает сохранённый серверный статус.
Порядок карточек внутри одной колонки и порядок колонок не сохраняются этим API.
Доска обновляется через `GET /task-board` раз в 20 секунд; кнопка «Обновить»
запрашивает данные сразу. Одновременно выполняется не больше одного GET.
Во время перетаскивания/удержания указателя, работы с формой и сохранения
автообновление пропускается. В фоне приложение не опрашивает сервер; при возврате
перечитывает доску. При закрытии экрана таймер отменяется.
Снимок применяется без полного удаления колонок: неизменённые карточки и
контроллеры сохраняются, как и горизонтальная прокрутка и раскрытые чеклисты.
Поздний GET, начатый до взаимодействия/сохранения, не заменяет новые данные.
При сетевой ошибке остаётся последняя доска с предупреждением об устаревании;
фоновые ошибки не создают повторяющиеся уведомления. Следующий опрос повторяет GET.
Порядок без серверного сохранения при обновлении возвращается к порядку API.
Если сервер возвращает `truncated`, показывается предупреждение: polling не
снимает лимит доски. Редактирование срока/состава подзадач и отдельное
архивирование задач ещё не подключены.

До релиза запланировано рассмотреть WebSocket или long polling для более быстрых
уведомлений об изменениях. Это отдельная доработка backend; текущие команды HTTP
и путь перечитывания/синхронизации доски можно сохранить. См. `.memory/backlog.md`.
