# Рабочая память CRM

updated: 2026-10-08
scope: Flutter frontend

Читайте этот файл на старте сессии. Остальная память — по поиску, не целиком.
Это текущее состояние; исторические результаты тестов и процессов проверяйте заново по необходимости.

## Где мы остановились

- Карточка клиента использует вложенные responsible/created_by, названия предпочитаемых филиалов через GET /branches (ошибка не блокирует карточку, остаётся ID), реальные даты регистрации/правки и три события activity в обзоре. Есть refresh списка/карточки, прокручиваемый адаптивный обзор. Ложные last-contact/«Нет визитов»/н/д убраны: API не даёт даты визита, не подменять её updated_at или событием задачи (FE-03/FE-13).
- Клиентские заметки подключены к реальному API: типизированные notes в деталях, создание/правка/архивирование (204), автор/время/version из сервера, ручной refresh. Список хранится в DetailPanel для сохранения между табами; сбрасывается при выборе другого клиента. При 409/неопределённом исходе нельзя повторять сохранение вслепую: сохранить черновик и перечитать данные. Авторство/модерацию проверяет сервер. См. FE-11; mock не адаптирован.
- FE-12: нейтральные колонки status=null по умолчанию, создание задачи в них получает new; перенос сохраняет реальный статус из ответа. «Активность» клиента подключена к GET activity с фильтром/пагинацией/refresh и инвалидацией после заметок/задач; actor может быть null, текста заметок нет. Меню задач открывает GET деталей и три истории, включая column_history. Отдельная вкладка клиента «История» остаётся заглушкой; realtime/mock для новых сценариев нет.
- Пользователь считает задачник завершённым для текущего этапа (не все возможности окончательно реализованы); следующий фокус — клиенты. Подключена форма создания из «+»: обязательные ФИО/DOB/источник и телефон либо email, необязательные пол/предпочитаемый филиал/ответственный. Справочники берутся из API, POST-ответ типизирован отдельно, после успеха перечитывается список. Старый mock не поддерживает этот сценарий; не выдавать его за проверенный реальный backend.
- Задачи и клиенты: единая запись видна на канбане и во вкладке клиента по GET /tasks?customer_id; привязка необязательна. Создание/редактирование имеет API-поиск клиента; PATCH отличает сохранение/замену/снятие связи. «+ Задача» закрепляет клиента; вкладка имеет пагинацию/refresh, меню и подзадачи. Обзор показывает первую new/in_progress/rework по серверной сортировке due_at (просроченные включены, без срока последние), пропуская завершённые страницы; срок/исполнитель из DTO. Назначение не меняет статус: «В работу» для назначенной new/rework, затем «Выполнено» из in_progress, через POST status; права проверяет сервер. Изменения карточки обновляют обзор/вкладку; автосинхронизации нет. См. FE-08/FE-09.
- Backend ведёт другой исполнитель и не синхронизируется с этой памятью. Его состояние здесь не отслеживать; совместимость проверять по подтверждённому API-контракту. Flutter уже передаёт access-токен backend для клиентских запросов; отдельный `mock_backend` остаётся для разработки UI.
- Flutter auth: вход переключает на форму обязательной смены временного пароля, `/auth/change-password` сохраняет новую пару токенов и открывает CRM. Access находится в памяти, refresh — в secure storage; Fresh обновляет access при ответе 401. SessionGate возвращает экран входа при потере сессии; явный logout очищает локальный токен. Восстановление входа после перезапуска не реализовано и отдельно не утверждено.
- Flutter: AppShell/sidebar, модуль клиентов, DTO, Dio repository, FutureBuilder/ListView; реальный GET списка с 10 демо-клиентами уже проверялся. Простой switch пересоздаёт экран/запрос; IndexedStack обсуждался, политика кэша не утверждена.
- Панель клиентов: серверный GET /customers?search ищет имя/телефон/email; debounce 300 мс, Enter сразу, очистка возвращает общий список. FutureBuilder отсеивает старые ответы, retry/создание сохраняют поиск, выбранная карточка не сбрасывается. Фильтры/пагинация панели пока заглушки, лимит 50 сохранён.
- Flutter: экран клиентов запускается с auth; в `modules/tasks/` есть канбан, DTO и формы создания задачи/колонки. POST-ответы сразу добавляются на доску; новая колонка доступна в форме задачи. Колонки отправляют `name` и выбранный `status`; задачи учитывают исполнителя и причину доработки по реальному контракту. Перенос между колонками сохранён через POST move с version/reason, серверной DTO и откатом/refresh при отказе (FE-10); in_progress → new запрещён сервером. Периодическое обновление и архивирование ещё не подключены. `mock_backend` имитирует auth и канбан в памяти процесса; данные сбрасываются при перезапуске, неподключённые команды предварительные.
- Карточки канбана оформлены отдельным `TaskCard`: целая DTO, естественная высота, приоритет, исполнитель, срок и прогресс. `TaskSubtasks` раскрывает чеклист; PATCH отметки отправляет done/version задачи, ответ заменяет DTO карточки и обновляет прогресс. При запросе чекбоксы блокируются, ошибка не меняет галочку. Авторство/исполнитель и закрытое состояние проверяются сервером. Дополнительных GET на каждую карточку нет; редактирование срока/состава подзадач ещё не подключено. `due_date` — календарная дата без пересчёта зоны.
- Колонки: рамка/фон на всю высоту, радиус 16, пунктир пустого состояния и нижней кнопки; AppFlowy сохраняет drag-and-drop. TaskColumnHeader показывает реактивный счётчик и меню переименования/архивирования через API; TaskColumnFooter открывает форму с initialColumnId. Последняя статусная колонка защищена; архивный перенос допускает нейтральную цель или совместимый статус, окончательная проверка серверная. Пустая нейтральная колонка архивируется без цели. PATCH имени отправляет version, не expected_version; status менять через PATCH нельзя. Архивирование отдельных задач ещё не подключено.
- Доска имеет нижний интерактивный Scrollbar, использующий горизонтальный контроллер AppFlowy; вертикальные уведомления колонок отфильтрованы. Если новое оформление AppFlowy не появилось после reload/restart, пользователь подтвердил необходимость полного закрытия и запуска приложения; не переписывать работающий дизайн до проверки фактического окна.
- Меню карточки справа от прогресса: редактирование названия/описания/важности (PATCH с version), назначение/снятие ответственного (POST assign с explicit nullable employee_id и необязательной причиной). Ответ обновляет DTO; непереданные срок, клиент и состав подзадач сохраняются. «Удалить задачу» отключён с пояснением — реального endpoint нет. Не имитировать удаление локально. Чеклист компактный, summary содержит выполнено/всего; PageStorageKey сохраняет раскрытие.
- HTML-шаблон: интерактивный канбан задач (FE-05), дашборд аналитики (FE-06) и каталог товаров/услуг (FE-07); всё на локальных демоданных, без утверждённых backend-контрактов. В навигации «Аналитика» и «Каталог» заменили самостоятельные пункты сотрудников/филиалов (ARCH-04); сущности и старые HTML-макеты сохранены.
- `gpt_template.html` теперь показывает четыре новые растровые концепции из `design_concept/` (клиенты, задачи, аналитика, каталог). Это НЕ интерактивная CRM: только переключатель изображений; новая компоновка ещё не утверждена и требует отдельной реализации. `crm_template.html` сохранён.
- Текущая задача памяти: Diary.md архивирован; новые записи только в .memory/. Старые записи о запуске PostgreSQL/uvicorn не означают, что процессы ещё работают.

## Ограничения, которые нельзя потерять

- Выделенная CRM на компанию, не SaaS; не добавлять tenant organization_id повсюду. Backend и frontend — отдельные репозитории.
- База — B2C-клиенты, сотрудники, филиалы, задачи; B2B, deals, loyalty, analytics — дополнительные модули. Не строить универсальный plugin framework заранее.
- Выбрана общая сборка всех официальных модулей, активность определяется лицензией на сервере. Скрытия UI недостаточно; отключение не удаляет данные.
- Клиент недоверенный; права/автор действия определяет сервер. Сотрудники видят всех клиентов, но доступ к задачам ограничивается филиалами.
- Backend: API → class UseCase.execute → repository; транзакция у use case, commit не скрывается в repository. ORM не возвращать через API. Для простого frontend-чтения отдельный use case необязателен.
- Источник первого привлечения, реферер и способ регистрации — разные факты. Повторные визиты/акции — отдельная история; её модель ещё не утверждена.
- Назначения и переходы сохраняются атомарно в типизированной истории; общий audit log её не заменяет. JSONB не заменяет известные поля/FK. Схема меняется новыми проверенными миграциями.
- Запросы Flutter создаются вне build(); State может уничтожиться при смене экрана. FutureBuilder не является постоянным кэшем. Мутация UI не равна сохранению: применять серверную DTO/версию и обновлять зависимые представления, учитывать конфликт/отказ и поздние GET (FE-10).

## Расхождения и открытые вопросы

- Отложен до релиза баг UI-AUTH-001: после смены раскладки в форме входа первый символ не вводится даже при фокусе/паузе. Только зафиксирован, причина не исследована; см. [bugs.md](bugs.md). Не исправлять в рамках канбана.
- Отложена оптимизация UI-SEARCH-001: локальные совпадения только как предварительный отклик, серверный поиск обязателен даже при совпадениях; кеш требует правил актуализации/прав. См. [backlog.md](backlog.md).

- Чтение клиентов/канбана адаптировано к API: клиенты из `items`; задача читает вложенные `customer`/`responsible`, nullable описание допустимо; при `truncated` есть предупреждение. Flutter отправляет выбранную незакрытую колонку без подмены (FE-05). API допускает отсутствие клиента/срока; вне `new` требует `tasks.move`. Форма проверяет исполнителя для `in_progress`/`completed`, причину для `rework`, отключает закрытые/неизвестные статусы и показывает сообщения ошибок 4xx без очистки ввода. Mock повторяет используемые POST-схемы, но не права и аудит; его предварительные PATCH/DELETE колонок пока не согласованы с подключённым реальным API (version, перенос в тот же статус).
- Клиенты: `home_branch_id` — необязательный предпочитаемый филиал и для новых, и для старых записей; отсутствие предпочтения не заменять выдуманным филиалом. Смысл филиала конкретного визита иной (DB-06). Создание с основным контактом и уникальность основного телефона/email — серверные правила; миграции backend проверяются отдельно, здесь их актуальное состояние не отслеживается.
- Не утверждены: visit/interaction/appointment и кампании; идентификация рабочего места; несколько backend на компанию; публичные контракты модулей и расширения карточек.
- До публичного развёртывания auth нужны HTTPS и проверка актуальных backend-защит; старые записи об отсутствии защиты от перебора/refresh-reuse не описывают текущий API (см. проверку в journal/2026-10.md).
- Backend-реализация и миграции больше не отслеживаются в hot memory frontend; перед зависимым изменением сверять актуальный API-контракт read-only или уточнять его у пользователя.
- В компактной карточке нужна давность визита вместо источника. API пока не возвращает last_interaction_at; название и тип учитываемого события предварительные.
- Обновления выполняет сотрудник поставщика; auto-update/MSIX лишь обсуждались. Не считать git pull процедурой бесшовного production-деплоя.

## Работа и источники

- Этот исполнитель занимается Flutter-клиентом и его отдельным mock-сервером. Backend ведёт другой исполнитель; не изменять и не синхронизировать его без нового явного поручения.
- Flutter/Dart объяснять постепенно; готовые SDK/пакеты рассматривать для всего стека. Не упрощать архитектуру из-за нехватки знаний пользователя. При выборе Flutter API сначала называть конкретный механизм и причину выбора; не перескакивать между ручным состоянием, готовыми компонентами и state-aware стилем без объяснения разницы и компромиссов.
- Не соглашаться с техническим предложением пользователя автоматически: оценивать последствия, прямо отмечать плохие решения и объяснять возражение. После возражения окончательный осознанный выбор пользователя имеет приоритет.
- Для MVP сначала доводить необходимые сценарии до рабочего состояния, не заниматься преждевременными оптимизациями. При этом сохранять чистые границы и типизированные контракты, чтобы улучшать продукт постепенно без глобального переписывания (WORK-04).
- Инструкции и `.memory/` локальны для frontend-репозитория и не зеркалируются в backend.
- Решения по теме: [архитектура](decisions/architecture.md), [backend/auth](decisions/backend.md), [frontend](decisions/frontend.md), [БД](decisions/database.md), [инфраструктура/лицензии](decisions/infrastructure.md), [процесс/память](decisions/collaboration.md).
- Хронология: journal/YYYY-MM.md. Формат, сроки и навигация: [README](README.md). Исходный дневник: legacy-journal.md — только при необходимости.
