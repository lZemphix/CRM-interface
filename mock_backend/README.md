# Mock backend

Отдельный **только локальный** FastAPI-сервер для разработки Flutter-интерфейса.
Возвращает три синтетические карточки клиента из `data.py` и изменяемый канбан
по образцу `crm_template.html`. PostgreSQL, Redis и основной backend не нужны.
Все изменения доски и тестовые сессии живут только в памяти процесса и пропадают
после перезапуска. Это не сервер для реальной работы компании.

## Запуск

Из корня репозитория:

```bash
cd mock_backend
uv python install 3.14
uv run uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

Нужен установленный `uv`; команды установят Python 3.14 и зависимости.
Затем в другом терминале запустите Flutter обычным способом. Сервер должен работать
на том же компьютере, что и нативный Flutter-клиент: в `ApiClient` уже указан
`http://127.0.0.1:8000`. Порт 8000 должен быть свободен.

Swagger UI: http://127.0.0.1:8000/docs

Не запускайте mock одновременно с настоящим backend на порту 8000. Mock рассчитан
только на `127.0.0.1`; не публикуйте его в сеть.

## Тестовая авторизация

В форме Flutter используйте логин `admin` и пароль `123456789098765`.
Это **открытые фиктивные данные**, не пароль реального администратора. Если нужно,
их можно заменить через `CRM_MOCK_LOGIN` и `CRM_MOCK_PASSWORD` перед запуском.

`POST /auth/login` принимает `{"login":"admin","password":"123456789098765"}`
и возвращает тот же формат пары токенов, что настоящий backend:

```json
{
  "access_token": "<случайный тестовый токен>",
  "refresh_token": "<случайный тестовый токен>",
  "token_type": "bearer",
  "access_expires_at": "2026-09-29T12:15:00Z",
  "refresh_expires_at": "2026-10-06T12:00:00Z",
  "must_change_password": false
}
```

Время в примере условное; сервер выдаёт актуальные значения. Access действует
15 минут, refresh — 7 дней. `POST /auth/refresh` принимает `refresh_token`,
возвращает новую пару и делает прежний refresh недействительным.
`POST /auth/logout` требует Bearer access и возвращает `204`.
Смена временного пароля не имитируется: `must_change_password` всегда `false`.
Все ручки, кроме `/health`, `/auth/login` и `/auth/refresh`, требуют Bearer.

## Контракт

Используемые Flutter поля ответов сверяются с действующими backend-схемами:

- backend `web/api/customers/schemas.py` задаёт поля ответов;
- backend `web/api/customers/views.py` задаёт пагинацию, ограничения ID и ошибки;
- Flutter `lib/modules/customers/models/customer.dart` разбирает эти ответы;
- `crm_template.html` используется только как источник синтетического содержания,
  но не как источник API-контракта.

Mock не является отдельным источником истины: при изменении backend-схем его нужно
обновлять одновременно с Flutter DTO. Заглушка не реализует все поля и правила
настоящего backend; известные отличия канбана перечислены ниже. Клиентские GET
требуют входа, как на настоящем backend.

`GET /customers?limit=50&offset=0` возвращает страницу с обёрткой `items`:

```json
{
  "items": [
    {
      "id": 1,
      "full_name": "Анна Петрова",
      "gender": "female",
      "date_of_birth": "1992-03-15",
      "status": "active",
      "primary_contact": "+7 916 233-10-45",
      "acquisition_source_name": "Instagram"
    }
  ],
  "total": 3,
  "limit": 50,
  "offset": 0
}
```

Дата рождения имеет формат `YYYY-MM-DD`. Поля карточки, заметки и контакты в список
не включаются.

`GET /customers/1` возвращает контракт `CustomerDetailsResponse`: идентификаторы
ответственного, автора, домашнего филиала и источника привлечения; код и название
источника; способ регистрации и реферера; `created_at`, `updated_at`; активные
контакты и заметки.

| Поле | Содержимое |
| --- | --- |
| `contacts` | `id`, `type`, `value`, необязательный `label`, `is_primary`, `created_at` |
| `notes` | `id`, `author_employee_id`, `text`, `created_at`, необязательный `edited_at` |

Задачи, взаимодействия и история назначений не входят в утверждённый ответ этой
ручки и должны подключаться через контракты соответствующих областей.

Заглушка принимает `1 <= limit <= 100`, `offset >= 0`; неверные значения дают
стандартную ошибку FastAPI `422`. За концом списка возвращается `items: []`,
при этом `total` сохраняет общее количество клиентов. ID клиента
ограничен диапазоном `1..2^63-1`; отсутствующий клиент возвращает тот же
машиночитаемый `404`, что и основной backend.

`GET /health` возвращает `{"status": "ok"}` — вспомогательная проверка этой заглушки;
формат ответа настоящего `/health` не подтверждён.

Создание и редактирование клиентов и заметок не имитируются. Кнопки в HTML-шаблоне
сами по себе не определяют утверждённый контракт backend.

## Канбан задач: предварительный контракт для Flutter

`GET /task-board` возвращает `columns`, `tasks` и `truncated: false`.
Каждая колонка содержит `id`, `name`, `status`, `order`, `counts_as_done`,
`version`, `archived_at`. Задача содержит `id`, `column_id`, `title`, `status`,
`priority`, `responsible_employee_id`, вложенные `responsible` и `customer`,
`due_at`, `branch_id`, `subtasks`, `version`. Вложенные объекты содержат `id` и
`full_name` либо равны `null`. Nullable `description` входит в ответ доски,
GET отдельной задачи и ответы команд, как в backend 0656dc5.
Подзадача содержит `id`, `title`, `done`, `order`. Прогресс карточки
вычисляется по `done` и количеству подзадач. `GET /employees` возвращает массив
`{"id":1,"full_name":"Ирина Ковалёва"}` для выбора исполнителя.

Пример задачи в ответе доски:

```json
{
  "id": 103,
  "column_id": 2,
  "title": "Исправить отображение карточки клиента",
  "description": "Проверить карточку после входа",
  "status": "in_progress",
  "priority": "high",
  "responsible_employee_id": 4,
  "responsible": {"id": 4, "full_name": "Администратор"},
  "due_at": null,
  "customer": null,
  "branch_id": null,
  "subtasks": [
    {"id": 1004, "title": "Воспроизвести ошибку", "done": true, "order": 0}
  ],
  "version": 1
}
```

| Действие | Запрос | Ответ |
| --- | --- | --- |
| Полная задача | `GET /tasks/{id}` | `200`, объект задачи |
| Создать | `POST /tasks` с полями формы и `subtasks: [{"title":"..."}]` | `201`, объект задачи |
| Сохранить форму | `PATCH /tasks/{id}` с изменёнными полями, `expected_version`; переданный список `subtasks` заменяет прежний | `200`, объект задачи |
| Отметить подзадачу | `PATCH /tasks/{id}/subtasks/{subtask_id}` с `{"done":true,"expected_version":1}` | `200`, объект задачи |
| Переместить карточку | `POST /tasks/{id}/move` с `{"column_id":3,"expected_version":1}` | `200`, объект задачи |
| Удалить задачу | `DELETE /tasks/{id}` | `204` |
| Добавить колонку | `POST /task-columns` с `{"name":"Блокировано","status":"new"}` | `201`, объект колонки |
| Переименовать | `PATCH /task-columns/{id}` с `{"name":"Ожидает ответа"}` | `200`, объект колонки |
| Удалить и перенести задачи | `DELETE /task-columns/{id}?move_to_column_id=1` | `204` |

Для `PATCH /tasks/{id}` новая подзадача приходит без `id`, существующая — с `id`;
отсутствующая в переданном списке удаляется. Если `subtasks` вовсе не переданы,
они не меняются. `due_at` принимает ISO 8601 со смещением часового пояса либо
`null`. `customer_id` и `branch_id` могут быть `null` для внутренних задач.
Если `expected_version` устарела, возвращается `409` с кодом `version_conflict`,
без изменения доски. Ошибки возвращаются в `detail: {code, message}`.

Создание колонок требует `status`: `new`, `in_progress`, `completed`, `rework`,
`confirmed` или `cancelled`. Для создания задачи разрешены первые четыре;
`in_progress`/`completed` требуют исполнителя, `rework` — непустую `reason`.
В Flutter закрытые колонки видны, но недоступны для создания задачи; выбранная
незакрытая колонка отправляется без подмены. Название колонки — до 60 символов,
описание задачи — до 4000, причина — до 1000, подзадач — максимум 50.

Известные отличия от реального API (на 07.10.2026):

- Mock и настоящий backend разрешают задачи без клиента и срока.
  `due_date` mock пока не поддерживает; Flutter создаёт точный срок через
  `due_at` или оставляет его пустым, но читает реальный `due_date` при отображении.
- Mock не воспроизводит права сотрудников (`tasks.move` нужен реальному API для
  создания вне `new`), аудит причины и проверку будущего срока. Это не средство
  проверки security/business-логики backend.
- В mock нет остальных полей подробностей, например автора и истории.
- Ещё не подключённые к Flutter команды mock используют `expected_version`,
  тогда как реальный сервер принимает `version`; DELETE задачи в mock не является
  реальным контрактом архивирования. Перед подключением этих действий нужно
  отдельно адаптировать ручки и тесты, а не ориентироваться на таблицу выше.
- Кнопка «+ Колонка» отправляет `name` и выбранный `status`, добавляет полученный
  объект на доску и в форму создания задачи без повторного GET. Mock не проверяет
  уникальность названий и не воспроизводит остальные ограничения управления
  колонками, например сохранение последней колонки каждого статуса.
  Форма ограничивает название 50 символами согласно текущему mock-контракту.
  Правила переходов, версий колонок и архивирования ещё не воспроизводят
  серверную бизнес-логику.

Здесь намеренно **нет** настоящих прав, бизнес-переходов статусов, аудита,
комментариев и постоянного хранения. Mock удаляет задачи из памяти, тогда как
реальный backend должен сохранять историю и архивировать. Связь произвольных
колонок с доменными статусами задана только в данных заглушки и не является
полной имитацией жизненного цикла задач.

## Изменение данных и проверки

Редактируйте список `CUSTOMERS` в `data.py`; с `--reload` сервер перезапустится сам.
Для пустого списка задайте `CUSTOMERS = []`. Данные не сохраняются в БД. У каждой
карточки должен быть хотя бы один контакт; остальные коллекции могут быть пустыми.
Стартовые колонки и задачи канбана находятся в `tasks.py`.

Из папки `mock_backend`:

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

Используются стандартные средства [FastAPI](https://fastapi.tiangolo.com/tutorial/response-model/)
для описания ответа и [TestClient](https://fastapi.tiangolo.com/tutorial/testing/)
для проверки HTTP-контракта.
