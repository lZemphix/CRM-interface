## BE-01 — Repository, DTO и use case

date: 2026-09-19
status: active
tags: backend, repository, use-case, dto, async, sqlalchemy

Decision:
Серверный сценарий — отдельный класс с execute(), зависимости через конструктор. API валидирует/сериализует и преобразует ошибки в HTTP; use case задаёт бизнес-действие и транзакцию; repository знает SQLAlchemy. ORM → application DTO → Pydantic response. Асинхронный I/O по всему пути.

Reason:
Пользователь выбрал единый стиль даже для сценария из одного запроса, чтобы не переучиваться на другую архитектуру.

Alternatives considered:
Свободные функции и прямые repository-вызовы из backend routes ради простоты не выбраны.

Affected areas:
application/customers/, database/repos/customers/, web/api/customers/

Notes:
Frontend имеет отдельное согласованное исключение: FE-02. Текущие use cases ещё импортируют concrete repository, AsyncSession/ORM для маппинга — абсолютная независимость от SQLAlchemy пока не достигнута. Это факт реализации, не новое архитектурное разрешение.

## BE-02 — Сотрудники, permissions и авторизация

date: 2026-09-19
status: active
tags: auth, security, permissions, employees, branches, registration

Decision:
- В MVP сотрудникам разрешён просмотр всех клиентов. Не добавляйте построчную изоляцию клиентов по ответственному сотруднику без нового требования; права на действия и административные возможности при этом остаются серверными.
- Самостоятельная регистрация B2C-клиента не входит в первый прототип: карточки клиентов создают сотрудники CRM. Поля и модель атрибуции не должны блокировать добавление самостоятельной регистрации в будущем, но её API и пользовательский сценарий сейчас не реализуются.
- Каждый сотрудник имеет отдельную учётную запись; общие аккаунты филиала не допускаются. Первого администратора создаёт сотрудник поставщика при установке и выдаёт одноразовый пароль, который необходимо сменить при первом входе.
- Права задаются отдельными разрешениями на конкретные действия внутри каждой категории: например, `customers.read`, `customers.create`, `customers.update`, `customers.archive`, `tasks.assign`, `audit.read`. Linux-модель `rwx` служила только ориентиром для объяснения и не должна реализовываться как общий набор букв или битовая маска.
- Сотрудник может состоять в нескольких филиалах, имея основной и дополнительные. Обычный доступ к задачам ограничивается филиалами сотрудника. Аналитика по умолчанию показывает основной/выбранный филиал, а просмотр сводной статистики всех филиалов предоставляется отдельным аналитическим модулем и правом.

Reason:
Сервер обязан устанавливать автора действий и права; роли и employee_id из клиента не доказывают личность.

Alternatives considered:
Числовые уровни Cisco/Linux и буквальная универсальная rwx-маска использовались лишь как аналогия.

Affected areas:
database/models/access.py; будущие auth dependencies и use cases

Notes:
Обсуждались access/refresh tokens; сроки, формат, ротация, хранение, отзыв ещё не утверждены. HTTP-авторизации пока нет; password/bootstrap подэтап реализован 2026-09-19 и ожидает ревью (см. журнал). Общая задача без branch_id и ограничение задач филиалами требуют отдельного правила доступа; не додумывать его при реализации.

## BE-03 — Подробная карточка клиента

date: 2026-09-19
status: active
tags: customer-details, api, 404, bigint, tests

Decision:
Одобренный контракт: GET /customers/{customer_id}, DTO с активными контактами/заметками; одинаковый 404 для архива и отсутствия; ID 1..2^63-1. Существующий ответ-массив GET /customers сохранён. acquisition_details и normalized_value не опубликованы.

Reason:
UI нужна карточка без скрытой загрузки ORM и без раскрытия архивных данных.

Alternatives considered:
Прямой возврат ORM и изменение формата списка в этом этапе не использованы.

Affected areas:
application/customers/dto.py; application/customers/use_cases.py; web/api/customers/; tests/test_customer_details*.py
